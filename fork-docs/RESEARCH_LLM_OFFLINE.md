# R8 — офлайн-инспектор LLM / перехват и повтор ответов

**Дата исследования:** 2026-10-30. **Кодовый срез:** `NeuralDao/inkos` `custom/main@f5c7473e4193134b7f8b48b7d5231531a548ca84` (последний слитый исходный код — `24bdd47c`, P1.2a/b локально и в GitHub `custom/main` не интегрированы). **Статус:** техническая возможность подтверждена статическим чтением кода и документации; решение о реализации и запуске проверок **не принято**.

## Краткий вывод

Отдельный HTTP-прокси, который перехватывает и модифицирует вызовы моделей и возвращает фиктивные ответы, реализуем. **Но для InkOS на данном этапе это избыточно.** Использовать встроенные мок-механизмы Vitest/LLM-клиента и существующий локальный fake-API в тестах. Вынести сначала узкую цель: инспектор фактически сформированных промптов и заранее заданные валидные ответы отдельных агентов. Не вмешиваться в production-путь генерации.

## Факты из проверенного кода

- `packages/core/src/llm/provider.ts`: общий `LLMClient`, фабрика `createLLMClient`, `chatCompletion`; варианты `apiFormat` и `stream` и несколько транспортных путей.
- `packages/core/src/agent/worker-agent.ts`: обычные текстовые вызовы идут через `chatCompletion`, а структурированные tool submissions через `guardedPiStream` / `guardedPiNonStreaming`; единый сетевой перехват потребует учитывать оба пути.
- `packages/core/src/agents/base.ts`: `BaseAgent` формирует/дополняет инструкции через `prepareWorkerMessages`, `authorRequest`, Skills; здесь логично инспектировать *эффективный* промпт, а не только первичный шаблон.
- `packages/core/src/__tests__/worker-agent.test.ts`: уже реализованы `vi.mock('../llm/provider.js')`, `vi.mock('../agent/pi-stream.js')`, синтетические `toolCall` и проверки передач параметров, без платного API.
- `packages/core/src/__tests__/longform-harness.flow.test.ts`: уже есть Node `createServer` на `127.0.0.1` с фиктивным OpenAI-compatible JSON `choices.message.tool_calls`, `stream:false`; этот путь используется в интеграционном сценарии PipelineRunner.
- `packages/core/package.json`: Vitest уже в devDependencies; отдельный сетевой HTTP-mocking пакет как прямую зависимость `core` в списке не видно.

## Три решения по возрастающей сложности

| Вариант | Возможности | Цена поддержки / риски | Оценка |
| --- | --- | --- | --- |
| A. Моки в текущих тестах (`vi.mock`, fake LLM + `prepareWorkerMessages`) | Проверка system/user/Skill/authorRequest и параметров, детерминированные структурированные результаты, режимы отказа/повтора, тесты русской локализации | **Низкая**; уже есть примеры и инфраструктура, но каждый тест должен иметь осмысленные валидные сценарии | **Рекомендуется первым** |
| B. Небольшой локальный fake-API или MSW внутри Vitest для отдельных интеграционных потоков | Содержимое HTTP-запроса и формат JSON/tools; последовательности «агент → ответ → следующий агент»; офлайн без отдельного долгоживущего сервиса | **Средняя**: разные API formats, tool calls и режимы `stream`; нужен fail-closed запрет случайных внешних вызовов | Если A недостаточно для P1.3/P1.4 или P1.M |
| C. Универсальный внешний прокси/record-replay | Перехват всех сетевых вызовов, просмотр/переписывание запросов, запись и повтор реальных ответов (после первоначального платного сеанса) | **Высокая**: порты/запуск, HTTPS/SSE, совместимость провайдеров и pi-ai, дублирование поддержки upstream, риск хранения секретов/черновиков, отдельный интерфейс и диагностика | Пока **не делать** |

Для варианта B не требуется новый сервис: `longform-harness.flow.test.ts` уже содержит рабочий пример простого Node-сервера. Vitest рекомендует [MSW](https://vitest.dev/guide/mocking/requests) для API-моков, но переход на новую зависимость нужно оправдать сложностью конкретных тестов.

## Поведение минимального безопасного офлайн-контура (проектные критерии, не реализация)

1. **Inspect:** получать окончательные сообщения перед моделью (включая Skills и authorRequest), имя агента, tool schema, модель и используемые настройки; сравнивать с ожидаемым и выдавать локальный диагностический отчёт. Не записывать токены доступа и приватные рукописи.
2. **Stub:** для заранее перечисленных сценариев возвращать валидные структурированные результаты Writer / Auditor / Reviser / Settler, включая `toolCall` и нужные поля; не выдавать одинаковое «OK» всем агентам. Непредусмотренный запрос **завершать ошибкой**, а не пересылать на платный API.
3. **Replay:** при реальной необходимости воспроизводить заранее записанные ответы. Исходная запись через реальный API один раз требует оплаты; новые версии промптов могут не совпасть с записью. Не предполагать, что replay проверяет выполнение новой инструкции моделью.
4. **Experiment/modify:** если хочется изменять промпт «на лету», разрешать это только в отдельном изолированном тесте: сравнивать `original` и `effective`, сохранять отчёт об изменениях. Иначе прокси способен **маскировать неисправность самого InkOS**, и тест проверит переписанный запрос вместо реальной реализации.
5. **Safety/Windows:** никаких фоновых обязательных сервисов; тестовый временный каталог и localhost; нулевой доступ к платным API в offline mode; запрет на передачу исходников/рукописей наружу; никакого CI/скриптов/конфигов без отдельного разрешения Codex.

## Что доказывает заглушка, а что нет

| Офлайн можно подтвердить | Офлайн нельзя подтвердить |
| --- | --- |
| Итоговый промпт требует русский результат и сохраняет нужный контекст; входные параметры, имя модели, tools и схемы согласованы; выход структурно валиден; состояние и границы локальных правок сохраняются; исключения/abort не ломают данные | Реальная модель выполняет инструкцию; русский текст получается естественным; диалоги и интрига хороши; выбранная температура улучшает качество; провайдер устойчиво поддерживает конкретные tool calls/streaming |
| Переходы пайплайна для **синтетического** ответа | Реальная независимость литературного Auditor от Writer и качество обнаруженных ошибок |

## Внешние существующие решения (кандидаты, не установлены)

- [Vitest: Mocking Requests](https://vitest.dev/guide/mocking/requests) рекомендует [MSW](https://mswjs.io/) для перехвата HTTP без изменения приложения, в Node и Vitest. Подходить к внедрению с проверкой текущей версии и лицензии.
- [MockServer Record & Replay](https://www.mock-server.com/proxy/record_and_replay.html) демонстрирует общий паттерн записи/повтора сетевых взаимодействий, но для личного InkOS это более тяжёлый вариант.
- [LangChain @langchain/net-mocks](https://github.com/langchain-ai/net-mocks) — готовый TS-сценарий HAR capture/replay; статус и поддержка вне LangChain, применимость к pi-ai и требования приватности ещё не проверены.
- [MSW HTTP reference](https://source.mswjs.io/docs/http/) — клиентонезависимые перехваты на Fetch API.

## Вывод и следующий шаг

**Исследовательский выбор:** вариант A — существующие моки, затем минимальный B при необходимости. Отдельный прокси C не предлагать как обязательный этап. Не принимать отдельную реализацию до завершения нынешней P1.2b или до выявления блокирующего кейса в P1.3. При разрешении подготовить Codex **одну узкую задачу**: офлайн-проверка реального итогового промпта + подставные structured tool responses на одном малом end-to-end сценарии. Никаких новых серверов и обязательных фоновых сервисов в первом шаге.
