## Дополнение: узкая проверка защиты `workspace__read` (30.10.2026)

**Кодовый срез:** `custom/main@968cbc03b06d532d38d054897a5781ad6bb635ad`; это **статическая** проверка реальных веток вызова, а не демонстрация утечки. Тестовый проект и реальная Studio-сессия не запускались.

**Проверенная цепочка полномочий:**

1. `harness/builtin-profiles.ts:14–21`: профиль `longform-novel` включает `workspace`. `harness/production-capabilities.ts:209–230` регистрирует агентный `workspace__read` с `scope:'project'` и риском `read`.
2. `harness/runtime.ts:221–228`: `isActionAuthorized()` возвращает `true` для `risk==='read'`, без отдельного авторского подтверждения.
3. `agent/agent-tools.ts:3050–3055,3057–3119`: при `params.path` путь разрешается **от корня проекта** и затем напрямую передаётся в `readFile(filePath,'utf-8')`; нет запрета для `.inkos/secrets.json`, `.env*`, `inkos.json`. `allowSystemPaths=false` не помогает: он запрещает лишь абсолютные пути с выходом из проекта, но не чувствительные файлы внутри проекта.
4. `llm/secrets.ts:14–21,34–45` сохраняет JSON с реальными `apiKey` внутри `.inkos/secrets.json`. `models/project.ts:21–45,93–110` **допускает** в `inkos.json` `llm.apiKey`, `researchSearch.apiKey`, `notify[].botToken/secret`, а также `llm.headers/extra` с потенциально секретным содержимым. Присутствие реальных ключей **в конкретном проекте не подтверждено**.
5. `utils/path-safety.ts:3–10` использует `resolve/relative` и блокирует простую `../`-траверсию, **но не проверяет файловую ссылку по фактическому realpath** (в т.ч. Windows junction). `agent/agent-tools.ts:3210–3250` при `workspace__grep` рекурсивно использует `stat` + `readFile`, так что редирект через ссылку — отдельный узкий случай для проверки. **Не утверждаем**, что такие ссылки уже существуют у пользователя.
6. **Хорошая уже существующая защита:** `harness/artifact-reader.ts:25–37` для ветки `readArtifactRevision` (запрос по `artifactId`) проверяет `realpath` в границах Work и SHA-256 содержимого. Не переносить диагноз произвольного `path` на этот другой механизм.

**Оценка:** достоверно подтверждён **недостаток контроля доступа** к файлам с конфиденциальными данными в `workspace__read`. Реальный запрос к LLM и утечка ключей **не воспроизводились**; штатный прямой Writer structured call без доступа к workspace-tools — не то же самое, что агентная Studio-сессия. Разумный приоритет — **P0-кандидат безопасности до использования модельного агентного чтения с настоящими API-ключами**, а не обязательная перепись всех инструментов InkOS.

**Узкое возможное задание Codex (только после отдельного разрешения):** защитить модельно-доступное чтение project files от credential paths и конфигураций с секретами; решение выбирать по минимальному изменению существующих инструментов и **не открывать дополнительный filesystem API**. Нельзя ограничиться запретом только одного `.inkos/secrets.json`: `.env`, `.env.local` и `inkos.json` со значениями секретных полей тоже должны быть безопасны. Отсутствие разрешённого абсолютного системного чтения само по себе не обеспечивает эту защиту.

**Офлайн-критерии безопасности на временном проекте с вымышленными sentinel-значениями:**

- `workspace__read` не возвращает секреты из `.inkos/secrets.json`, `.env`, `.env.local` или сырого `inkos.json` с заполненными credential fields; результат и ошибка не содержат sentinel. Наличие секретов в пользовательском проекте не предполагается заранее.
- Успешно продолжают читаться штатные главы, канон, Skills и явно загруженные пользователем материалы (`works/...`, допустимые `.inkos/uploads/...`), а ветка `artifactId` остаётся работоспособной.
- Простые `../` пути отклоняются как прежде; физическая переадресация пути за пределы разрешённой области, включая Windows link/junction при поддержке тестового окружения, **не позволяет обойти запрет**. Если создание ссылки невозможно без Windows Developer Mode, это отмечать как SKIP, а не PASS.
- Проверить, что другое модельно-доступное чтение (`workspace__grep` и другие затронутые пути) не обходит ту же защиту; не расширять в рамках этого запроса весь storage/harness.
- Проверять **результат реального инструментального вызова**, а не только helper unit test. Никаких сетевых запросов и реальных credential fixtures; токены/секреты не писать в GitHub/логи.

**Граница:** фиксируем проверенное и предложенные критерии, не создаём новую кодовую ветку, не запускаем Codex, тесты или Studio. Без отдельного разрешения это не implementation task. Изменения остаются внутри `fork-docs/`.
