## P0 — воспроизводимая Windows-среда

**Цель:** один проверяемый способ разработки/запуска форка на Windows/pwsh, без потери исправлений при сборке.

1. Проверить и исправить конфликт настроек pnpm между локальным pnpm 12 и текущими `package.json`/`pnpm-workspace.yaml`, сохранив нужные dependency overrides и разрешения lifecycle-скриптов. Уточнить, какую версию pnpm использовать для форка.
2. Исправить dev-запуск Studio, чтобы корнем был выбранный проект книги, а не `../..` (путь до исходников); предпочтительна кроссплатформенная конфигурация без WSL2.
3. Выбрать безопасный запуск CLI из локальной сборки; отдельно оценить состояние зависимостей после прежнего `npm link`. Не предлагать массовый `pnpm install` без необходимости/согласия.
4. Для P0 согласовать короткую локальную проверку: версию CLI, корректный запуск Studio и API, минимальную проверку сборки. Наличие PASS — только по фактическому логу пользователя.

**CI на `custom/main`:** потенциально полезно, но не блокер для одиночного локального вайб-кодинга. Рассматривать отдельно как P2, поскольку сейчас используются локальные тесты.

## P1 — качественная русскоязычная литература

**Принятое направление: русскоязычная читательская поверхность при англоязычном рабочем конвейере.** Не переводить встроенные промпты, профессиональные Skills, служебные записи, ключи JSON, enum-значения и существующие алгоритмы «на русский». Внутренние инструкции и канон могут оставаться английскими; модель должна выдавать **художественный результат на русском** там, где это запрошено. Скрытый язык рассуждений модели не поддаётся проверке и не является системным контрактом.

**P1.1 — Языковая маршрутизация без китайского fallback (исторический блокер 1.8).** В v1.8 `utils/language.ts::inferLanguage` не учитывал кириллицу, поэтому русский текст мог определяться как `zh`. Пользователь успешно обходил блокер добавлением `А-Яа-яЁё` к распознаванию латинских символов и направлял рабочий процесс по ветке `en`. В 2.0 старый `inferLanguage.ts`/`language.ts` отсутствует: исследовать фактический путь выбора `language` в CLI, Studio, Work и книге; не копировать замену строк из `dist`. Обеспечить, что русский ввод **не направляет** внутренний конвейер в `zh`. Сохранить рабочий `en` для служебного конвейера; при необходимости ввести **отдельный явный целевой язык текста** (`ru`), не заменяя им повсеместно внутренние enum.

**P1.2 — Точечные языковые контракты в корневых промптах результата.** Для структурированного Writer в 2.0 (`submitStructured` → `runWorkerAgentTool`) задать русский язык только в полях `title`/`content` итоговой главы; для Reviser — в выдаваемом художественном тексте. Служебные карточки, world rules, планы, JSON-поля, tool calls и текст профессиональных Skills сохранить на исходном языке. При необходимости отдельно проверить читательские аннотации/экспорт, но не вводить универсальное «всё человекочитаемое — по-русски». Не патчить глобально `runWorkerAgent()`/`runWorkerAgentTool()`; старый глобальный `RU_SURFACE_CONTRACT` из 1.8 не переносить.

**P1.3 — Аудит всех счётных конструкций и Unicode-совместимость.** В ходе статического просмотра кода подтверждены разные места:
- `packages/core/src/utils/length-metrics.ts`: регулярка `en_words` `[A-Za-z0-9]` не считает кириллические слова; `zh_chars` считает непробельные символы, что не эквивалентно словам;
- `packages/core/src/utils/source-text.ts`: отдельная метрика `englishWords` на латинице. **Она не ошибочна сама по себе** — оценить, где нужна дополнительная русская метрика, не менять смысл существующей;
- `packages/core/src/models/length-governance.ts`: схема знает только `en_words`/`zh_chars`;
- `packages/core/src/state/chapter-word-sync.ts` и `packages/core/src/pipeline/runner.ts`, `chapter-review.ts`: потребители метрик для сохранения, ревью и синхронизации;
- `packages/core/src/agents/short-fiction.ts`: подсчёт длины, разбиение на партии и эвристический лимит токенов; проверять отдельно, если расширяется поддержка короткой прозы.

Подобрать **один проверяемый механизм подсчёта русской прозы** (Unicode-aware и корректный для кириллицы), применить минимальные адаптеры без изменения английских и китайских измерений. Отдельно проверить русские/латинские слова вперемешку, `ё`, цифры, дефисы, тире, Markdown, переносы, кавычки, сохранение главы, последующий пересчёт и ограничения длины. Не принимать русский текст с `wordCount=0`, не допускать циклов исправления из-за ошибочной метрики. Полный поиск по всем пакетам завершить в ходе реализации; приведённый перечень — подтверждённые точки, а не гарантия исчерпывающего охвата.

**P1.4 — Сопоставимая литературная проверка.** После технического вертикального среза сравнить русские главы на одинаковых исходных условиях: естественность, имена/термины между английским каноном и русским текстом, причинность, стиль, повторы, стоимость и объём. Платные LLM-эксперименты только с разрешения пользователя и в согласованном бюджете.

**Порядок:** сначала P0 Windows/pnpm/Studio, затем узкая реализация P1.1–P1.3 через Codex, затем локальная проверка пользователя и отдельно P1.4. Не смешивать с полной русификацией Studio или переделкой harness.

## P2 — экономичность и удобство

- **Не создавать ролевой роутер с нуля:** `ProjectConfigSchema.modelOverrides` и `PipelineRunner.resolveOverride` уже существуют. Изучить реальные ограничения, возможности per-agent reasoning/temperature и полноту учёта токенов; оптимизировать после измерений.
- Изучить фактический цикл `ContinuityAuditor` / `ReviserAgent`, частоту ревизий и расходы **на реальных примерах**, прежде чем менять пороги или поведение ревью.
- Оценить целесообразность CI для `custom/main` и расхождение pnpm 9 в workflow с локальным окружением. Без автоматического дорогостоящего тестирования по каждому коммиту.
- Удобство Studio/Windows по подтверждённым проблемам.

## P3 — идеи

- Полная русская локализация интерфейса Studio, если базовые сценарии уже работают и есть практическая потребность.
- Новые форматы литературы, интеграции и инфраструктура — только если доказана польза для главной цели.
