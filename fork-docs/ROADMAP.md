## P1 — качественная русскоязычная литература

**Статический языковой аудит выполнен 29.10.2026**: [LANGUAGE_AUDIT.md](./LANGUAGE_AUDIT.md). **Принятое направление: форк генерирует литературу ТОЛЬКО по-русски; сначала русский художественный longform, затем русскоязычные авторские документы и отчёты при сохранении англоязычных инструкций.** Встроенные системные промпты, профессиональные Skills, JSON-ключи, enum, ID и алгоритмы не переводить. На этапах P1.1b–P1.3 рабочие планы, канон и служебное состояние остаются EN, **но это временная политика, не архитектурный запрет на RU**. В P1.5–P1.7 отдельно локализовать содержимое отчётов, планов, карточек, канона и, после проверки рисков, служебных сведений. Язык системной инструкции агента не обязан совпадать с языком выходного артефакта. Скрытый язык рассуждений модели не поддаётся проверке и не является системным контрактом.

**Единственный целевой язык литературного вывода — RU.** Латиница и другие письменности внутри русской прозы допустимы по жанру и канону: названия компаний/брендов, технические термины, аббревиатуры, индексы, цитаты и собственные имена; не навязывать тотальную транслитерацию/перевод, не запрещать смешанные письменности. Использовать операционный EN для текущего конвейера; EN/ZH художественный результат не поддерживать как отдельную продуктовую цель. Существующие языковые enum, tools и форматы InkOS 2.0 не удалять автоматически: самостоятельная переработка схем/Studio в P1.2 не входит. Основание — [DECISIONS.md](./DECISIONS.md).

**Один активный продуктовый маршрут:** `longform-novel` (создание книги → последовательные главы → аудит → ревизия → сохранение состояния → возобновление → экспорт). Другие творческие режимы не адаптировать под RU до полной отладки longform, кроме устранения подтверждённых общих блокеров; существующую работу остальных режимов не ломать.

### Обязательные контрольные точки G0–G4 для longform

**Градации проверок (уточнено 31.10):** A — точечные unit/schema/fake-LLM проверки после изменений; B — сборка, typecheck, целевые интеграционные проверки и offline dry-run на границах модулей; C — последовательный реальный API-прогон с сохранением артефактов, аудитом, ревизией и разбором качества. **G1/C — через бесплатный `openrouter/free`, не платный.** При техническом FAIL на A/B реальный C не запускать. Обязательная проверка является условием приёмки этапа, **не** автоматическим запуском после каждого коммита. По умолчанию проверки выполняет пользователь на Windows; Codex не запускает install/build/test/typecheck/E2E/Studio/API без явного конкретного разрешения.

**Трёхконтурная стратегия (30.10.2026):** (1) детерминированные моки/fake-API — основной обязательный контур A/B; (2) **необязательная** микромодель на локальном CPU — только после фактического smoke-теста оборудования/API и лишь для проблем, которые моки не воспроизводят; (3) **реальные OpenRouter-прогоны** в контрольных точках C; **G1 использует только `openrouter/free`**, а дальнейшие G2–G4 требуют самостоятельного согласования модели/режима. Реальные API не запускать автоматически; перед каждой проверкой — разрешение пользователя и ограничение числа запросов, а при платном режиме — бюджета. Если микромодель не поддержит нужные tool calls/контекст, считать это ограничением тестового инструмента, а не дефектом InkOS. Не строить прокси или зависимость от Ollama как часть production-пайплайна.
