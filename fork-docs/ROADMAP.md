## P1 — качественная русскоязычная литература

**Статический языковой аудит выполнен 29.10.2026**: [LANGUAGE_AUDIT.md](./LANGUAGE_AUDIT.md). Проверены ключевые цепочки Longform, Short Fiction, Harness, CLI/Studio, Skills, сохранение и экспорт; в отчёте различаются подтверждённые проблемы и ещё не проверенные runtime-гипотезы. **Это не разрешение на кодовую реализацию.**


**Принятое направление: форк генерирует литературу ТОЛЬКО по-русски; сначала русский художественный longform, затем русскоязычные авторские документы и отчёты при сохранении англоязычных инструкций.** Встроенные системные промпты, профессиональные Skills, JSON-ключи, enum, ID и алгоритмы не переводить. На этапах P1.1b–P1.3 рабочие планы, канон и служебное состояние остаются EN, **но это временная политика, не архитектурный запрет на RU**. В P1.5–P1.7 отдельно локализовать содержимое отчётов, планов, карточек, канона и, после проверки рисков, служебных сведений. Язык системной инструкции агента не обязан совпадать с языком выходного артефакта. Скрытый язык рассуждений модели не поддаётся проверке и не является системным контрактом.

**Единственный целевой язык литературного вывода — RU.** Латиница и другие письменности внутри русской прозы допустимы по жанру и канону: названия компаний/брендов, технические термины, аббревиатуры, индексы, цитаты и собственные имена; не навязывать тотальную транслитерацию/перевод, не запрещать смешанные письменности. Использовать операционный EN для текущего конвейера; EN/ZH художественный результат не поддерживать как отдельную продуктовую цель. Существующие языковые enum, tools и форматы InkOS 2.0 не удалять автоматически: самостоятельная переработка схем/Studio в P1.2 не входит. Основание — [DECISIONS.md](./DECISIONS.md).

**Один активный продуктовый маршрут:** `longform-novel` (создание книги → последовательные главы → аудит → ревизия → сохранение состояния → возобновление → экспорт). Другие творческие режимы не адаптировать под RU до полной отладки longform, кроме устранения подтверждённых общих блокеров; существующую работу остальных режимов не ломать.

**P1.1b — язык книги и маршрутизация: ЗАВЕРШЕНО.** [PR #3](https://github.com/NeuralDao/inkos/pull/3), реализация `03f1e080`, merge `24bdd47c`. Проверка локального Codex: G0 — 80 точечных тестов PASS; G1 — четыре typecheck PASS; G2 — Core build, штатные Studio server и CLI typecheck PASS. Глобальные служебные enum, Studio UI language, Writer/Reviser-промпты, счётчики длины, экспорт и другие творческие режимы не русифицировались. Для успешной генерации русской прозы обязательны следующие отдельные этапы P1.2 и P1.3.

**P1.2 — языковой контракт художественного longform Writer/Reviser: РАЗРЕШЕНО, НЕ РЕАЛИЗОВАНО.** Два последовательных узких задания в одной рабочей кодовой ветке, промежуточное независимое ревью после P1.2a, затем P1.2b и итоговая приёмка. Код меняет только локальный Codex; документацию — ChatGPT. Новый рабочий branch и кодовые изменения — только после актуальной сверки GitHub/локальной базы; ранее Codex подтвердил чистый синхронизированный `custom/main@09aa5a17` (до последующих документационных коммитов).

- **P1.2a — Writer:** в `agents/writer-prompts.ts` использовать существующий `resolveNarrativeLanguage(book)` для целевого языка результата `submit_chapter_draft.title/content`, отдельно от операционного `book.language`. Единственный продуктовый сценарий — **EN/RU**; в существующей реализации допустимые EN/ZH и ZH/EN не требуют отдельной литературной оптимизации и не должны задерживать приёмку P1.2a. Не ломать общие технические интерфейсы без причины. Сохранить методику, контекст, авторские факты и структуру tools. Русский текст может содержать Nike, Microsoft, Apollo-1, международные обозначения, английские термины и цитаты. Точные авторские названия и зафиксированные каноном написания сохранять; англоязычная запись во внутреннем плане сама по себе не запрещает естественную русскую форму. Не менять творческий вызов в `writer.ts`, Settler и глобальный harness без доказанной необходимости. Проверять исходный шаблон **и эффективные сообщения** после `prepareWorkerMessages()` со штатным Skill и authorRequest. Если автор явно задал иноязычное название главы, требование точного названия имеет приоритет над автоматическим переводом.
- **Контрольная точка A:** ревью диффа P1.2a (ACCEPT/REVISE/REJECT) до работы над Reviser. Точные тесты промптов и сборки сообщений можно написать, но без отдельного разрешения не запускать.
- **P1.2b — Reviser:** `pipeline/runner.ts` передаёт целевой язык в `agents/reviser.ts` отдельно от операционного `language`. Все режимы `polish/rewrite/rework/anti-detect/spot-fix`: при RU-книге русский художественный язык для `submit_revised_chapter.revisedContent` и **только заменяемых** `range_N_content` при локальной правке. Проверить обе ветки spot-fix: выбор диапазонов через `submit_chapter_edit_ranges` и прямой `targetText` без этого вызова. Защищённые фрагменты неизменны, даже если их исходный язык другой. Не переопределять ограничения каждого режима и не менять текстовые range schemas.
- **Контрольная точка B:** независимое итоговое ревью P1.2 и точечные детерминированные проверки при отдельном разрешении; EN/ZH-художественные книги не входят в целевую поддержку форка; сохранять общие интерфейсы InkOS 2.0 там, где это практически полезно, без обязательной побайтовой идентичности историческим промптам. Не заявлять проверенное качество русской прозы по наличию инструкций. Один общий PR после разрешения пользователя.
- **Границы:** внутренние Skills/планы, служебные schemas, Settler/StateValidator, метрики, заголовки, EPUB, Short Fiction и глобальные `runWorkerAgent()`/`runWorkerAgentTool()` не изменять в P1.2. Произвольные пользовательские Skills/authorRequest могут намеренно конфликтовать с языком книги: проверить штатный маршрут, зафиксировать ограничение, не обещать невозможного универсального отсутствия конфликтов. Старый `RU_SURFACE_CONTRACT` из 1.8 не переносить.

**Обнаруженный отдельный пробел до платной G1:** `utils/chapter-document.ts` сохраняет заголовок `# Chapter N:` при операционном EN, а `interaction/export-artifact.ts` выставляет EPUB `lang=en`; один P1.3 со счётчиками это не решит. Предварительно разделить последующую работу на **P1.3a — Unicode-метрики** и **P1.3b — читательские заголовки/roundtrip/EPUB metadata**. Обе — отдельные будущие задачи до G1, пока не разрешены к реализации.

**P1.3a — Аудит всех счётных конструкций и Unicode-совместимость.** Счётчики должны корректно обрабатывать русские слова, вкрапления латинских терминов, брендов, аббревиатур, цифр и индексов; не использовать запрет латиницы как способ исправления метрики. В ходе статического просмотра кода подтверждены разные места:
- `packages/core/src/utils/length-metrics.ts`: регулярка `en_words` `[A-Za-z0-9]` не считает кириллические слова; `zh_chars` считает непробельные символы, что не эквивалентно словам;
- `packages/core/src/utils/source-text.ts`: отдельная метрика `englishWords` на латинице. **Она не ошибочна сама по себе** — оценить, где нужна дополнительная русская метрика, не менять смысл существующей;
- `packages/core/src/models/length-governance.ts`: схема знает только `en_words`/`zh_chars`;
- `packages/core/src/state/chapter-word-sync.ts` и `packages/core/src/pipeline/runner.ts`, `chapter-review.ts`: потребители метрик для сохранения, ревью и синхронизации;
- `packages/core/src/agents/short-fiction.ts`: подсчёт длины, разбиение на партии и эвристический лимит токенов; проверять отдельно, если расширяется поддержка короткой прозы.

Подобрать **один проверяемый механизм подсчёта русской прозы** (Unicode-aware и корректный для кириллицы), применить минимальные адаптеры без изменения английских и китайских измерений. Отдельно проверить русские/латинские слова вперемешку, `ё`, цифры, дефисы, тире, Markdown, переносы, кавычки, сохранение главы, последующий пересчёт и ограничения длины. Не принимать русский текст с `wordCount=0`, не допускать циклов исправления из-за ошибочной метрики. Полный поиск по всем пакетам завершить в ходе реализации; приведённый перечень — подтверждённые точки, а не гарантия исчерпывающего охвата.

**P1.4 — Сопоставимая литературная проверка: СКВОЗНАЯ.** Проводить не только в конце: первая оценка на G1 после P1.2a/b–P1.3a/b, повторная на G3 и финальная на G4. Сопоставлять русские главы при одинаковых исходных условиях: причинность, интрига, персонажи, естественность русского, стиль, повторы, соблюдение канона, полезность аудита и ревизии, стоимость и объём. Разделять технический PASS и литературный ACCEPT/REVISE; не выводить качество из одного суммарного балла без примеров.

**P1.5 — Русскоязычные отчёты литературного аудита и ревизии.** Для `ContinuityAuditor` и связанных литературных проверок выдавать понятные русские объяснения наблюдений, аргументацию и рекомендации, сохраняя стабильные коды, типы, ссылки на строки и технические поля. У Reviser прежде всего возвращается исправленный текст; предусмотреть понятную сводку изменений, предпочтительно на основе фактического диффа и наблюдений без обязательного дополнительного LLM-вызова. Не превращать служебный state в русский побочным эффектом отчёта. Приёмка G2.

**P1.6 — Русскоязычные авторские документы longform.** Планы и мемо глав, сюжетные арки, карточки персонажей, библия мира, правила и читаемый автором канон — создавать/хранить на русском в отдельном явно выбранном режиме. Английские инструкции агентов и схемы сохранять. Проверить `Architect`, `Planner`, `Composer`, поиск контекста, обновление и повторное чтение документов; начинать новый RU-режим без обязательной автоматической конвертации старых книг.

**P1.7 — Язык служебных фактов и состояния longform.** Проверить `Settler`, `StateValidator`, state projections, факты, summaries и сюжетные hooks. Решить на фактических тестах, какие значения полезно хранить по-русски, а какие технические структуры оставить языконезависимыми с русским представлением для автора. Не менять ID, JSON-ключи, enum, ссылки и формат событий. Обязателен контроль возобновления серий и согласованности текущих сохранённых данных; поддержку legacy-форматов не навязывать. Приёмка P1.6–P1.7 на G3.

### P1.M — мультимодельный longform: обязательная подготовка до платной G1

**Текущий выбор: только недорогие открытые модели (с проверяемой доступностью весов и лицензией), через используемый роутер; закрытые дорогие модели GPT/Claude/Gemini не включать в тестовые конфигурации без нового явного решения пользователя.** Оплата API для доступных через роутер открытых моделей допустима на согласованных контрольных прогонах. Модельный состав не фиксировать только по названию или цене из старого PDF: перед тестом подтвердить API ID, действующий тариф, контекст, лимит вывода, tool calling, режим reasoning и пригодность для русского. Подбирать **разные семейства/разработчиков** хотя бы для Writer, `ContinuityAuditor` и Reviser, чтобы снизить коррелированные ошибки. Разные названия моделей сами по себе не доказывают независимость.

В коде **уже есть** `ProjectConfigSchema.modelOverrides` и `PipelineRunner.resolveOverride()` — новый роутер не создавать. Перед G1 точечно проверить маршрутизацию каждого реального вызова и фиксацию выбранной модели, поддержку per-agent `thinkingBudget`/`temperature` (сейчас отсутствуют в `AgentLLMOverrideSchema`), характеристики переиспользуемого LLM-клиента, поддержку structured tools, retries и учёт токенов. Writer сейчас также выполняет `settle()` — это потенциально дорогая общая модель для творческой и служебной фаз. **Не разделять агента преждевременно:** проверить фактические расходы/качество и затем при необходимости назначить отдельную узкую задачу.

**Протокол независимости:** аудитор проверяет главу и канон по подтверждаемым наблюдениям со ссылками на фрагменты, а не на «авторитет» Writer; по возможности не передавать ему идентификатор модели-автора. Reviser исправляет доказанные проблемы, не принимает автоматически каждую оценку. Повторная проверка контролирует дифф, новые ошибки и нарушение границ правки. Для отладки сравнить одномодельную baseline и мультимодельную конфигурацию на сопоставимых исходных данных; решение принимать по качеству и ошибкам, а не только по расходам.

### Обязательные контрольные точки G0–G4 для longform

**Градации проверок:** A — точечные unit/schema/fake-LLM проверки после изменений; B — сборка, typecheck, целевые интеграционные проверки и offline dry-run на границах модулей; C — последовательный реальный прогон через платный API с сохранением артефактов, аудитом, ревизией и разбором качества. При техническом FAIL на A/B платный уровень C не запускать. Обязательная проверка является условием приёмки этапа, **не** автоматическим запуском после каждого коммита. По умолчанию проверки выполняет пользователь на Windows; Codex не запускает install/build/test/typecheck/E2E/Studio/API без явного конкретного разрешения.

После G4 — решение о готовности longform и только затем переход к другим режимам. |

**Один повторяемый художественный тестовый сценарий:** отдельный Windows-проект с заданными персонажами, правилами мира, конфликтом и ожидаемыми проверяемыми фактами. Для каждой G-точки фиксировать HEAD, идентификаторы/версии моделей, аргументы reasoning, промпты или их контрольные хеши, token usage по агентам, фактические списания роутера, ошибки/повторы, результат PASS/FAIL и литературные замечания с примерами. Сохранять трассы и артефакты приватно, не публиковать рукописи/ключи/детальные пользовательские расходы в публичном GitHub. Сравнение при одинаковых исходных условиях не гарантирует статистической достоверности: малые выборки считать инженерной диагностикой.

**Платные прогоны разрешаются отдельно:** перед каждой точкой C пользователь утверждает конкретный набор открытых моделей, сценарий, ориентировочный бюджет и предел расходов. Не включать автоматические расходы в CI. При ошибке на ранней главе остановить последовательность и разбирать её, а не оплачивать весь пакет. До выполнения обязательной проверки отмечать соответствующий этап как `NOT VERIFIED`, а не `PASS`.

**Порядок:** P0, P1.1a и P1.1b/G0 завершены → P1.2a/b–P1.3a/b и P1.M/G1 → P1.5/G2 → P1.6–P1.7/G3 → G4 и решение о готовности longform → другие режимы. Технические зависимости могут потребовать узких промежуточных исправлений, но не полной русификации Studio и не переработки harness ради будущих функций.

## P2 — экономичность и удобство

- **Не создавать ролевой роутер с нуля:** минимальная проверка существующих `modelOverrides` и per-agent reasoning/temperature нужна в P1.M **до G1**; дальнейшие оптимизации стоимости/маршрутизации оставлять здесь после измерений.
- Изучить фактический цикл `ContinuityAuditor` / `ReviserAgent`, частоту ревизий и расходы **на реальных примерах**, прежде чем менять пороги или поведение ревью.
- Оценить целесообразность CI для `custom/main` и расхождение pnpm 9 в workflow с локальным окружением. Без автоматического дорогостоящего тестирования по каждому коммиту.
- Удобство Studio/Windows по подтверждённым проблемам.
