# Аудит языковых контрактов InkOS 2.0

**Дата:** 29.10.2026. **Проверенная ветка:** `NeuralDao/inkos/custom/main`; **коммит исходного кода и документации:** `02756a4aae0ca9231d90ee3c72dd7e22d7127352`; последний кодовый коммит до документации — `2de9ac5`.

**Актуализация после аудита:** [PR #3](https://github.com/NeuralDao/inkos/pull/3) интегрирован в `custom/main@24bdd47c` (29.10.2026): необязательный `BookConfig.narrativeLanguage` и передача через CLI/Studio/Work/Core теперь реализованы. Ниже сохранён **исторический статический аудит на `02756a4`**; фразы «предлагается» и «отсутствует» относятся к старому снимку. Writer/Reviser, Unicode-метрики, сохранение и экспорт русской прозы по-прежнему требуют отдельных этапов P1.2–P1.7.

**Задача:** установить, **кто, где, как и для какого артефакта выбирает язык**, включая пути ввода, промпты и Skills, структурированные tools, внутренние данные, ревизии, измерение длины, импорт, сохранение и экспорт. Цель форка — оригинальная русская художественная проза с англоязычным внутренним конвейером, **без перевода исходных Skills и корневых механизмов**.

## Метод и пределы

По GitHub Git tree проверены **907 элементов / 799 blobs**, без усечения. Классифицированы 277 рабочих TS-файлов Core, 55 CLI, 133 Studio, 38 Markdown-документов Skills и 218 тестовых файлов. Прочитаны исходники ключевых сквозных путей, все **38** поставляемых Skill/справочных Markdown, выборочные тесты и источники других производственных методов. Для точечных цитат ниже указаны номера строк кодового снимка; файлы могут сдвигаться при обновлениях.

**Это глубокая статическая ревизия критических маршрутов, но не машинно-проверенный grep всех 799 blobs и не запуск собранных промптов.** Нельзя заявлять, что найдены абсолютно все вхождения во всех исходниках и пользовательских дополнениях. Рабочие книги, пользовательские Skills и активные/внешние контексты не доступны в этом GitHub-снимке. Не выполнялись install, build, тесты, Studio, API и платные LLM-вызовы.

**Термины:**
- **Operational language** (`language: en/zh`) — текущая рабочая ветка исходного фреймворка; выбор шаблонов, служебных форматов и маршрутов.
- **Narrative/output language** — **предлагаемое** отдельное свойство для читательской прозы (например, `ru`); в исходниках **пока отсутствует**.
- **UI/assistant response language** — язык чата, надписей, сообщений пользователю; не равен языку внутренних артефактов.
- **Counting mode** — `en_words/zh_chars`, определяет меру объёма, а не язык служебного промпта.

## В. Все найденные **разновидности** языковых указаний

1. **Явное требование конкретного языка содержания:** `architect.ts:65-70` (English foundation), `state-validator.ts:42-44` (English state report). Эти команды **правильны для своих артефактов**.
2. **«Отвечай на языке пользователя»:** поставляемые Skills `inkos-story-review/SKILL.md:16`, `inkos-story-deslop/SKILL.md:14`, `inkos-short-writing/SKILL.md:25`, `inkos-story-import/SKILL.md:18`, Skills анализа рынка/литературы и обложек. Это относится к ответу/результату текущей операции, **не всегда** к служебному state.
3. **Язык промпта без прямого приказа языку текста:** `writer-prompts.ts`, `reviser.ts`, `prompts/short-fiction.ts`. Английская формулировка сама по себе НЕ равнозначна `Write in English`; не объявлять её автоматическим конфликтом.
4. **Маршрутизация/скрытый fallback:** `harness/production-capabilities.ts:188`, `harness/tools/longform-production.ts:132`, `harness/tools/short-production.ts:34`, `cli/commands/init.ts:17`, `studio/api/book-create.ts:51`, `studio/api/server.ts:180,4804-4806`. Значения кроме `en` часто становятся `zh`.
5. **Формат/обёртка:** `chapter-document.ts:4-25`, `chapter-splitter.ts:6-33`, `interaction/export-artifact.ts:114-131`, state projections (английские таблицы/заголовки).
6. **Единицы длины, validation и бюджеты:** `length-metrics.ts`, `length-governance.ts`, `source-text.ts:44-50`, `agents/short-fiction.ts:58-64,660+`, `runner.ts:272-273`, `chapter-review.ts:59-65`. **Нельзя** трактовать `ru_words` как `zh`.
7. **Язык интерфейса/чата:** `studio/lib/app-language.ts:3`, `studio/pages/LanguageSelector.tsx:3-10`, `studio/App.tsx:167-214`, `studio/api/server.ts:4112-4126,5529-5535`, `cli/localization.ts:21-39`, `cli/tui/i18n.ts:166-192`. ## Г. Сборка **реального** промпта: ещё один слой

На уровне агентов `agents/base.ts:107-164` функция `prepareWorkerMessages()` добавляет `currentExecutionAuthorRequest` как **system-message**, выбирает профессиональные Skills, гидратирует их references, строит компилированный контекст. `agent/worker-agent.ts:324-328` затем соединяет system messages и инструкцию обязательного вызова tool; сам этот слой **не** задаёт художественный язык.

Следствие: проверять только строку `buildWriterSystemPrompt()` **недостаточно**. Нужна проверка после `prepareWorkerMessages()`, где уже присутствуют реальные, доступные для теста Skills, author request, Work/context. Пользовательские Skills, локальные `.inkos/profiles`, отдельные авторские запросы и внешние ссылки способны внести непредвиденную инструкцию. Часть из них отсутствует в публичном GitHub.

**Заранее известная ловушка:** текст русского запроса пользователя может попасть в служебный Agent как авторитетное требование. Контракт «русский только в художественных полях» должен не вводить его в заблуждение: для Architect / Planner / Settler результат остаётся EN; для Writer / Reviser — RU, а правила и tool names остаются EN.

Кеш Agent в `agent/agent-session.ts:886` учитывает изменение текущего `language`. Если позже добавлять независимое `narrativeLanguage`, потребуется проверить, когда перестраивается контекст верхней сессии; **не предполагать**, что кеш автоматически замечает новое поле.

## Д. Счётчики, безопасность данных и неизменяемые контракты

- `length-metrics.ts:22` применяет `/[A-Za-z0-9]+(?:'[A-Za-z0-9]+)?/g`. Русские слова без латиницы получают `0`; неверная длина может запустить false `CHAPTER_LENGTH_OUT_OF_RANGE` и пересчёт.
- `source-text.ts:50` имеет поле `englishWords` — **оно правильно называется English**, бездоказательно заменять его нельзя. Для смешанного/русского документа нужен отдельный тип измерения по назначению.
- `runner.ts:272-273` и `chapter-review.ts:59` делают вывод о языке **из counting mode**. Это место разорвать при появлении `ru_words` (рабочий language остаётся EN).
- `state/chapter-word-sync.ts:41-79` использует BookConfig language для пересчёта уже сохранённых глав: изменение метрики не должно самовольно менять чужие книги.
- `agents/short-fiction.ts:660+` оценивает output tokens коэффициентом, рассчитанным для ZH/EN; при RU может быть слишком оптимистичен либо неэффективен. Измерять на примерах, не принимать числа на веру.
- `utils/chapter-document.ts` и `interaction/export-artifact.ts` используют language документа и book.language; русский файл может сохранять английское `Chapter N` и EPUB `lang=en`, даже если `title/content` русские.
- `models/runtime-state.ts:3` фиксирует `zh/en` для служебного state. **Не расширять его до `ru`**, если состояния остаются английскими.
- В `writer.ts:329-345` chapter summary от Settler может содержать русское название полученной главы, даже при английских остальных полях. Уточнить политику для **названий и собственных имён**, не переводить идентификаторы наугад.

## Е. Рекомендуемая стратегия (ещё **не** разрешённая реализация)

1. **Сохранить `en` и `zh` без замены.** В рабочей книге добавить *необязательный* целевой язык литературной выдачи (например, `narrativeLanguage: "ru"`). Это **проектная рекомендация**, схемы пока такого поля не содержат.
2. **Единственный контракт на артефакт, не глобальная инъекция.** На этапе построения системного промпта Writer/Reviser **подставлять** точное требование к языку полей готовой главы; если в исходном шаблоне уже есть такое требование, заменять его, а не добавлять противоположное. Не перехватывать все `runWorkerAgent` или `runWorkerAgentTool` и не редактировать установленные dist-файлы.
3. **Внутренние операции не трогать.** English foundation, plans, agent Skills, state, схемы и enum — исходные. Точечная EN-уточняющая инструкция Settler допускается **только если реальная проверка** покажет дрейф внутренних записей от русской главы.
4. **Отдельно разделить `operationalLanguage`, `narrativeLanguage`, `document/metadata language`, `countingMode`.** Минимальное количество новых полей и адаптеров, без глобального рефакторинга для всех жанров.
5. **Два вертикальных среза:** сначала longform Writer/Reviser + сохранение/export + счётчик + ошибки маршрутизации; затем отдельно short-fiction. Другие Work Profiles не затрагивать без запроса.

## Ж. Проверки для будущего задания Codex — без платных API

**Сухая проверка эффективных промптов (без LLM):**
- EN/EN: Writer/Reviser/system messages не меняются относительно upstream для той же книги.
- EN/RU: `title/content`, `revisedContent` и range replacement имеют **ровно одно однозначное** требование русской прозы, даже после добавления Skills и authorRequest.
- Architect, Planner, Settler, StateValidator, forecast при EN/RU по-прежнему создают/обрабатывают служебные записи на EN.
- Runtime message/tool schemas сохраняют ID, JSON keys и enum. `Respond in the user's language` в Skills не должен перетянуть служебный формат.

**Метрики и сохранение:**
- Unicode: `ё/Ё`, дефисы и тире, цифры, английские имена в кириллическом тексте, кавычки, Markdown frontmatter, пустой документ; не считать русский текст нулём.
- Write → review → revise → state settlement → save → chapter-word-sync → export → import/roundtrip; русский заголовок и EPUB lang, без повторного заголовка и потери глав.
- Regression: неизменность английских и китайских книг; короткая проза не считается поддержанной, пока её отдельные проверки не выполнены.
- Без зависимости от наличия внешних paid API: unit tests и заданные fake/stubbed tool responses. **Codex не запускает** build/test/typecheck/install без конкретного разрешения пользователя.

## З. Итог аудита

**Подтверждено:** две языковые оси в одной `language` мешают честной поддержке русского; сквозной маршрут EN/RU должен быть реализован на **границах артефактов**, а не одним глобальным промптом. Наибольшие риски: fallback RU→ZH, конфликты authorRequest/Skills, метрики, состояние после русской главы, двойная локализация заголовков и экспорт, отдельная короткая проза.

**Не подтверждено:** отсутствие всех возможных противоречий в финальных runtime-промптах; успешный русскоязычный запуск 2.0; литературное качество/стоимость; полнота статического анализа всех runtime-путей/пользовательских дополнений. Проверка фактически собранных сообщений и синтетические интеграционные сценарии должны быть частью будущей ограниченной Codex-задачи.

**Код не менялся. Платные вызовы и тесты не запускались.**
