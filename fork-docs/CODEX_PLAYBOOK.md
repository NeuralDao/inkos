# Codex: модели, делегирование и экономичная реализация InkOS

## Активный режим 31.10–04.11.2026 — Codex как независимая проверка

**Приоритетная временная инструкция**, подробности — [WORKFLOW.md](./WORKFLOW.md). В ближайшие пять календарных дней **ChatGPT сам пишет согласованный код и тесты в отдельной GitHub task-ветке и публикует draft PR**, не затрагивая `custom/main`. **Codex не должен повторно разрабатывать эту задачу**: на Windows он открывает подготовленный PR, сверяет базу/цель/дифф, указывает ошибки с file:line, по необходимости делает узкие правки **в той же ветке** и запускает **только отдельно разрешённые** проверки. Потом ChatGPT проводит финальное ревью; пользователь отдельно разрешает merge. Это экономит лимит Codex на генерацию кода.

**Минимальное задание Codex:** «Проверь PR #… (`NeuralDao/inkos`, base `custom/main`) как независимый ревьюер. Не переписывай готовую реализацию и не расширяй scope. Проверь соответствие цели, совместимость, тестовые случаи и риски; исправь только подтверждённые дефекты в той же ветке. Без моего отдельного разрешения не запускай install/build/test/typecheck/lint/E2E/Studio/API и не делай merge. Дай ACCEPT/REVISE/REJECT, файлы, находки, фактически выполненные PASS/FAIL/NOT RUN». Для важного PR допускается короткий независимый обзор в Codex, но без повторного полного исследования ChatGPT.

## Главная цель и базовый режим

Мы развиваем `NeuralDao/inkos`, рабочая ветка `custom/main`, ради **качественной, связной, интересной и экономичной оригинальной русской литературы**. Не оптимизировать количество коммитов или скорость генерации кода в ущерб результату Writer/Reviser, памяти/канону, длине глав, стоимости и воспроизводимости.

**Текущая привычная настройка пользователя — GPT-6.1 Sol / Medium для всех задач Codex.** Она остаётся **контрольной базой**, пока новая схема не проверена. Планируемый переход — **выбирать модель на задачу**, а не менять глобальные конфигурации без разрешения. Модель в Codex и модели художественных агентов InkOS через OpenRouter — **две независимые системы**; это руководство относится только к **разработке**.

| Когда | Предварительный выбор | Признак правильного применения |
| --- | --- | --- |
| Узкий поиск по репозиторию, перечисление вызывающих мест, карта файлов, проверка фактических зависимостей | **GPT-6 Luna / Low**, если доступна | Только чтение, точные пути/строки, минимум интерпретаций; при сложной семантике передать Sol |
| Небольшой локализованный баг/рефакторинг, ясный контракт и тест-кейсы, ограниченное число файлов | **GPT-6.1 Terra / Medium** | Один исполнитель, малый понятный diff, отсутствие случайных изменений |
| Сопоставление нескольких подсистем, спорный контракт, сложные регрессии, выбор архитектурного решения | **GPT-6.1 Sol / Medium** | Понимает всю цепочку и риски, выбирает минимально достаточную архитектуру |
| Уязвимость, границы доверия, опасные изменения данных, повторяющийся FAIL без ясной причины | **Sol / High по необходимости**, сначала анализ | Не поручать безопасность только дешёвой модели и не принимать решение без независимого ревью |
| Несколько независимых **исследований**, каждое с чётким результатом | **Sol / Medium координатор + 1–2 Luna/Terra** | Параллельные контексты дают пользу; координатор проверяет свидетельства |
| Простая задача с последовательными зависимыми действиями | **Одна Terra или Sol**, без субагентов | Нет затрат на координацию без выгоды |

**Не принимать API-прайс за цену подписочного Codex:** API Terra дешевле Sol, но расход включённой квоты Codex зависит от объёма и шагов; сравнивать фактическую **цену принятой задачи**, включая переделки. Уровни и доступность моделей проверять по реальному списку клиента; имя модели в рекомендациях не гарантирует её доступность.

## Как выбирает ChatGPT перед заданием Codex

1. По коду **нужного коммита** и цели определить область, риск и критерии приёмки; проверить локальную базу через Codex до начала записи. GitHub `custom/main` не показывает незакоммиченные изменения локальной ветки.
2. Выбрать **одну основную модель и усилие**; в задании указать коротко «рекомендуется Terra Medium» или «оставить Sol Medium». Если выбор не поддерживается в установленном клиенте — использовать доступную Sol Medium, не блокировать задачу.
3. Для неоднозначной, рискованной или межмодульной задачи — **Plan Mode** на границы и точки проверки; если ChatGPT уже разобрал код и дал узкие критерии, не требовать второй большой план ради формальности.
4. Делить крупную работу на проверяемые этапы с промежуточным diff/review. **Один этап — один владелец изменений;** следующий только после результата предыдущего. Не превращать каждую мелочь в отдельный Issue или PR.
5. После исполнения: ChatGPT независимо проверяет полный diff и свидетельства, выдаёт **ACCEPT / REVISE / REJECT**. Это не merge-разрешение.

### Субагенты Codex: когда и как

**Использовать только если есть минимум два независимых вопроса**, например (а) найти все потребители метрик Unicode и (б) проверить существующее тестовое покрытие; (а) путь выбора модели и (б) fake-API fixtures. У каждого субагента: **один вопрос, границы путей, ожидаемый ответ (файл:строка → наблюдение → риск → предложение)** и явное «не менять файлы». Главный Codex проверяет выводы, не просто склеивает их.

- **Начальный потолок проекта — 2 параллельных субагента** (не системная гарантия); не запускать вложенные волны и не делегировать автоматически каждую подзадачу. Если один справится — выбрать одного.
- Встроенные роли Codex: `explorer` (исследование), `worker` (исполнение), `default`; отдельные локальные кастомные TOML-роли возможны **позже**, только если повторяющаяся польза доказана. **Не создавать сейчас `.codex/agents/`, `AGENTS.md`, менять `~/.codex/config.toml` или глобальные инструкции.**
- В Codex Desktop субагентам можно выбирать модели и уровни рассуждения в поддерживаемой версии, в том числе модель при делегировании; **сначала проверить возможности именно локального приложения**. Не путать их с `multi_agent.enabled` из отдельных **Agents API / Responses API**, за которые выставляется отдельный API-счёт.
- **Инструкция «только чтение» — не техническая изоляция.** Субагенты наследуют разрешения и среду главной сессии. Для настоящего read-only нужен соответствующий режим sandbox/permission у **родительской** сессии. В режиме реализации ограничивать изменения основным Codex, избегать параллельной записи в одни файлы. Никакие субагенты не обходят запреты на тесты, внешние вызовы и секреты.
- **Стоп-условия:** ответы повторяются; приходится постоянно синхронизировать файлы; контекст уже понятен; расходы растут без новых свидетельств. Тогда отказаться от субагентов и продолжать одним исполнителем.

**Пример формулировки делегирования** (после разрешения на конкретную задачу):

> Основной Codex — Sol Medium. При реальной независимости можно привлечь максимум двух субагентов. `explorer` на Luna Low: найти конкретные пути вызовов, вернуть file:line и возможные пропуски; `explorer` на Terra Medium: проверить имеющиеся тестовые сценарии и контракты, вернуть пробелы и минимальные тест-кейсы. Субагенты не меняют файлы, не запускают команды проверок. Главный агент сверяет факты, принимает решение, выполняет согласованный diff и останавливается для независимого ревью.

## Полезные возможности Codex без новых конфигураций

- **`/model` / выбор модели в UI:** выбирать подходящую модель для отдельной сессии или задачи. Не менять глобальный default без сравнения.
- **`/plan` / Plan Mode:** только при существенной неопределённости. План фиксирует путь; не расширяет пользовательское разрешение.
- **`/goal` / Goal:** долговременная **цель внутри поддерживаемой сессии** для многошаговой согласованной работы; не разрешает неограниченное автономное изменение файлов, PR, merge или будущую фоновую работу. Использовать, если клиент поддерживает.
- **`/side` / side chats:** вопросы о решении Codex, не отвлекая основной поток выполнения; применять там, где доступно.
- **`/review`:** локальная предварительная проверка diff Codex; **не заменяет независимое ревью ChatGPT**.
- **`/status`, `/compact`, `/fork`:** контроль сессии/лимитов, уплотнение накопленного контекста, развилка обсуждения вместо потерянного контекста. Команды/названия зависят от версии и платформы — проверить UI, не считать автоматически установленными.
- **Skills, MCP, GitHub:** применять только если подходят конкретной задаче. Сторонние инструкции/данные и PR считать недоверенными; не давать доступ к приватным рукописям и ключам ради удобства. Подключение нового сервиса, внешняя публикация и запись в GitHub — отдельные разрешения.

## Неподвижные ограничения проекта

- **Стандартная норма после временного режима:** код, тесты, CI, зависимости, скрипты и конфигурации меняет Codex; ChatGPT редактирует `fork-docs/`. **Исключение 31.10–04.11.2026 имеет приоритет:** согласованный код/тесты в task-ветку GitHub коммитит ChatGPT, открывая draft PR; Codex независимо ревьюит и при необходимости исправляет. `fork-docs/` по-прежнему ведёт ChatGPT.
- По умолчанию **только чтение/анализ**; реализация — после прямого разрешения пользователя на задачу. Ни `/goal`, ни субагент, ни Plan Mode не создают отдельного разрешения.
- Без явного согласования не запускать **`pnpm install`, test, lint, build, typecheck, E2E, Studio, CI, платные LLM API или многократные диагностические циклы**. Разрешено написать тесты, прочитать существующие и предложить команды проверки; фактические PASS только по реальным отчётам.
- Windows + **PowerShell (`pwsh`)**, репозиторий `C:\Projects\inkos`. Не переключать `master`/`upstream-main`, не делать force push. Patch незакоммиченных изменений и отчёт сохранять в **`C:\Projects\inkos-review-artifacts\<task-id>\`**; передать файл в ChatGPT (локальные пути недоступны). Для GitHub PR — только по разрешению.
- Не публиковать приватные главы, материалы автора, `.env`, `.inkos/secrets.json`, `inkos.json` с ключами и логи с токенами. **P0-файловая защита интегрирована через [PR #12](https://github.com/NeuralDao/inkos/pull/12)**: типичные очевидные пути модельного чтения закрыты для локального InkOS, но это не защита от преднамеренной локальной подмены файлов (TOCTOU/hardlink). Не открывать новый аудит безопасности без доказанного практического дефекта; работы с реальными API-ключами и платные прогоны всё равно требуют отдельного разрешения.
- **Успех = минимум корректных изменений + доказанный технический результат + последующая независимая литературная проверка G1/G3/G4**. Никакие кодовые тесты сами по себе не означают качественной русской прозы.

## Пробный переход с Sol Medium на Terra Medium

**Первый подтверждённый пробный кейс (30.10.2026): Terra Medium** оформила принятый P1.3b в один commit `966eca21`, обычный push и [PR #6](https://github.com/NeuralDao/inkos/pull/6), без посторонних файлов, конфликтов и повторных тестов; ChatGPT независимо сверил все **8/8 Git blob SHA** и принял PR, позднее он объединён обычным merge `58c0851`. Это подтверждает пригодность Terra для **ограниченных механических Git/PR-операций**, но **не подтверждает** качество кодинга и снижение расхода подписочной квоты: измерений нет. Следующие небольшие изменения кода — отдельные пробы после проверки актуальной базы; P1.M маршрутизация и security поначалу остаются Sol Medium/High. Это не новая обязательная веха ROADMAP.

Для каждого пробного задания: модель/effort, реальный scope, длительность или измеримый расход по доступному индикатору, количество существенных возвратов **REVISE**, финальное **ACCEPT/FAIL**, реально запущенные проверки. **Сравнение с прежним Sol Medium качественное до накопления сопоставимых задач**: не заявлять «50% экономии Codex» по API-тарифам. Если Terra провоцирует дорогие переделки, вернуться к Sol.
