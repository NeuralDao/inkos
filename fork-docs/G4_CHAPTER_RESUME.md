# Восстановление конвейера главы: `write resume`

## Для чего нужна команда

`inkos write resume [book-id] [chapter]` продолжает незавершённую операцию над главой с сохранённой контрольной точки. Она выполняет ещё не подтверждённые этапы до сохранения главы и состояния. Команда не начинает следующую главу и не является синонимом `write sync` или `write rewrite`.

Обычный `write next` останавливается, если предыдущая операция главы не отмечена завершённой, и предлагает сначала выполнить `write resume`. Это предотвращает случайный переход к следующей главе при незакрытом конвейере.

## Запуск из PowerShell

Из корня проекта книги:

```powershell
Set-Location C:\Projects\inkos-g4-workspace
$cli = 'C:\Projects\inkos-merge-custom-main\packages\cli\dist\index.js'
node $cli write resume 'dogbook01' 3 --json
if ($LASTEXITCODE -ne 0) { throw 'Восстановление главы завершилось с ошибкой.' }
.\scripts\check-pipeline.ps1 -BookId 'dogbook01' -Chapter 3
```

Подставьте фактические project root, путь к собранному CLI, id книги и номер главы. Книгу можно не указывать, только если в project root есть ровно одна книга; при нескольких книгах CLI просит указать id. Номер главы можно не указывать — тогда выбирается последняя контрольная точка книги. `check-pipeline.ps1` — отдельный проверочный скрипт из workspace книги, не часть команды `resume`.

## Что сохраняется и как выбирается точка продолжения

- Контрольные точки лежат в `.inkos/chapter-runs/<encoded-book-id>/chapter-<номер>-<operationId>.json` внутри project root. Запись содержит версию формата, книгу, главу и последовательные записи этапов со статусом, временем и данными результата.
- До продолжения проверяются книга/глава, baseline runtime state, стабильные исходники книги и идентичность конфигурации. Если они изменились относительно сохранённой операции, `resume` останавливается с ошибкой безопасности данных.
- Для запросов моделей фиксируются attempt id, порядковый номер и fingerprint входа. Сырой ответ worker сохраняется в `.inkos/agent-runs/<book-id>/worker-responses/` до последующей обработки. При прерывании ответ можно обработать локально повторно только при совпадении идентичности и входа; это не новый сетевой вызов.
- При отсутствующем или неоднозначном raw-ответе, изменившемся запросе, испорченной контрольной точке или конфликте с уже записанной следующей главой команда останавливается. Не следует вручную объявлять этап завершённым только по наличию текста или расходу токенов.
- Для некоторых старых глав без checkpoint предусмотрен ограниченный bootstrap по согласованным артефактам и журналу. Поддерживается только безопасно подтверждаемая граница; при недостатке доказательств команда остановится.

Основные этапы long-form операции: baseline и входы, план и контекст, текст черновика, первичный аудит, ревизия (если она требуется), settlement, проверка истины/канона, повторный аудит редакции и итоговая запись. Уже завершённые результаты берутся из checkpoint, если их входы совпадают; успешное завершение `persisted` делает повторный `resume` идемпотентным.

## Ошибки, повторные вызовы и границы безопасности

- Сбой до сохранения главы оставляет контрольную точку и доступные артефакты для продолжения. Сбой модели сам по себе не разрешает бесконечный автоматический retry.
- Если поток оборвался после получения ответа, сначала используется сохранённый raw response. Если безопасно сопоставить его с запросом нельзя, повторная обработка не подменяет ответ новым результатом автоматически.
- Ошибка первичного аудита, отсутствие применимого результата ревизии или несогласованное состояние могут оставить главу сохранённой, но pipeline отмечается незавершённым. `write next` в таком случае блокируется до восстановления или явного исправления состояния.
- Версия Ревизора проходит техническую проверку перед принятием и settlement. Канон и производные файлы должны строиться от версии, которая фактически принята как текст главы.
- Повторный аудит после принятой редакции предназначен для заметок к вычитке. Его недоступность/неполный результат записывается как предупреждение и сам по себе не должен отменять уже принятую редакцию или блокировать завершение главы. При невалидном структурированном ответе диагностический raw response остаётся в worker archive; отображаемая заметка может сообщать только причину недоступности, а не извлекать из сырого ответа непроверенные выводы.
- Если `resume` сообщает `CHAPTER_RESUME_REQUIRED`, запустите его для той же книги и главы. Если получен `CHAPTER_RESUME_INPUT_CHANGED`, `CHAPTER_RESUME_CHAPTER_CHANGED`, `CHAPTER_RESUME_NOT_LATEST` либо ошибка baseline, сначала разберите изменившиеся артефакты; не удаляйте checkpoint наугад.

`write sync` пересобирает производные данные и выполняет аудит, но не продолжает все редакторские этапы. `write rewrite` повторно пишет главу и не заменяет безопасное восстановление сохранённой операции.

## Проверки и ограничения

Автотесты контрольных точек покрывают идентичность операции, повторное использование этапов, защиту от изменённых входов, ошибки восстановления и блокировку перехода к следующей главе. Они не доказывают надёжность конкретного провайдера или полный платный сквозной прогон. Расход при реальных неудачных запросах следует сверять с OpenRouter billing; внутренний token usage не всегда равен биллингу провайдера.

Пользовательские прогоны `dogbook01`, глава 3, подтвердили восстановление части этапов, сохранение редакции и канона и ручную диагностику через `check-pipeline.ps1`. В одном прогоне аудит не выдал доступный результат; в следующих успешный повторный аудит не всегда проходил проверку доказательств. После последующих изменений post-audit-поведения тесты и сборка **NOT RUN**. Полный платный сквозной прогон с текущей редакцией **NOT RUN**.

Текущая реализация и документация должны оставаться согласованными: повторный аудит — вычиточные заметки; первичный аудит, применение редакции и техническая проверка состояния остаются отдельными условиями готовности. Не считайте предупреждение повторного аудита доказательством исправления исходной находки.
