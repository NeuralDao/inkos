# Правила работы над InkOS

## Временный режим экономии лимитов Codex — 31.10–04.11.2026

**АКТИВЕН; пересмотр 05.11.2026.** По прямому решению пользователя на пять календарных дней **этот раздел имеет приоритет над постоянными правилами ниже**, где написано «ChatGPT не изменяет код», «Codex — единственный исполнитель» или «разработка на паузе». При продлении — новое явное решение; без него с 05.11 возвращается стандартное распределение. Старые правила сохранены как постоянная база, а не как действующий запрет в этот период.

**Роли:** ChatGPT — технический исполнитель согласованных изменений: анализирует **актуальные файлы и commit `custom/main`**, принимает ограниченные архитектурные решения, **пишет исходники/тесты** и коммитит их **только в отдельную task-ветку** `NeuralDao/inkos`, публикует **draft PR** с base `custom/main`, критическими рисками, перечнем файлов, точными критериями и честным `NOT RUN` для непроведённых проверок. Если draft PR технически недоступен, допускается обычный PR с явной пометкой `DRAFT — DO NOT MERGE`; не подменять PR архивом патчей. Файлы `fork-docs/` ChatGPT по-прежнему ведёт самостоятельно.

**Codex — независимый ревьюер и ограниченный корректор:** при возвращении пользователя к Windows-репозиторию получает **ссылку/номер PR**, проверяет базу и diff, ищет дефекты и несовместимости, исправляет только конкретные подтверждённые ошибки **в той же ветке**, сообщает точные PASS/FAIL/NOT RUN и риски. Не заставлять Codex заново выполнять исследование, проектировать задачу или переписывать уже готовое решение. Пригодность реализации подтверждается независимым просмотром, а не фактом публикации PR.

**GitHub — единственный штатный канал передачи кода:** ChatGPT → task-ветка → draft PR → Codex review/corrections → итоговое ChatGPT ACCEPT/REVISE/REJECT → пользователь решает merge. Никаких ZIP/patch-файлов через пользователя, **если GitHub доступен**; локальные артефакты — запасной вариант при недоступности GitHub или незафиксированных локальных изменениях. Не делать прямых кодовых коммитов в `custom/main`, `master`, `upstream-main`, force-push, merge или развёртывание без отдельного явного разрешения.

**Разрешения и ресурсные пределы:** это делегирование меняет **исполнителя**, но **не расширяет объём каждой задачи**. Код, ветка, commit и PR допустимы в пределах прямо согласованной задачи без повторного разрешения на каждый шаг; новые крупные задачи — после согласования. Платные LLM/API, операции с приватными данными, запуск G1, изменение production, установка зависимостей, test/build/lint/typecheck/E2E/Studio/CI по-прежнему требуют конкретного разрешения. Если проверка не выполнена — `NOT RUN`, не `PASS`. Не коммитить API-ключи, `.env`, личные рукописи или секреты. Если создание PR автоматически включает CI, зафиксировать это и не утверждать, что CI не исполнялась.

**Приоритет качества:** минимальные независимые изменения, понятные diff/тесты, воспроизводимые сценарии в Windows/PowerShell. Для подготовки G1 сохранять штатный OpenRouter Responses API, пока реальная несовместимость не доказана; устаревший локальный patch переключения транспорта **не накатывать автоматически**. Техническое ACCEPT не разрешает merge и не доказывает качества русской прозы.


## Продуктовый фильтр (обязателен при анализе, заданиях Codex и ревью)

1. **Назначение:** только качественная оригинальная литература на русском языке; рабочие системные инструкции, Skills, JSON, IDs и состояние InkOS 2.0 можно сохранять на английском, если это надёжнее и проще. Не требовать от модели определённого языка скрытых рассуждений.
2. **Смешанное написание:** русский текст может включать Nike, Microsoft, Apollo-1, NASA, названия компаний, технические термины, обозначения, цитаты и собственные имена в исходном написании, если это естественно для произведения. Не вводить проверки «только кириллица», насильственный перевод или транслитерацию. Приоритет — явно заданная автором форма и утверждённый канон.
3. **Нулевая потребность в legacy:** у пользователя пока **нет ни одного существующего проекта/книги InkOS**, в том числе созданного на старой версии. Поэтому миграции прежних форматов, backward compatibility, адаптеры старых API/интерфейсов, сохранение исторических промптов **не требуются по умолчанию**. Делать только при конкретном доказанном практическом сценарии. Не ломать общие механизмы актуального InkOS 2.0 без причины.
4. **Не наращивать лишнее:** полноценные EN/ZH-литературные сценарии, переводческий конвейер, общие языковые роутеры и архитектура «на вырост» — вне целей форка без отдельного решения. Перед новой задачей указать её пользу для RU-longform, минимальные затрагиваемые файлы, риски и цену сопровождения. Удаление прежних интерфейсов ради чистоты не является самостоятельной задачей.

Эти ограничения применяются к будущим техническим решениям; не расширяют ранее согласованное P1.2a. См. [DECISIONS.md](./DECISIONS.md) и [ROADMAP.md](./ROADMAP.md).

## Два постоянных рабочих контура

**Исследования — самостоятельная, повторяемая работа ChatGPT, а не подготовительная подсекция разработки.** Цикл: конкретный вопрос → необходимые код/источники → факты против гипотез → рекомендация/решение/ограничение → фиксация существенного результата в `fork-docs/`. После G1/G3/G4 исследуем уже **сгенерированную** прозу, качество и расходы; после новых моделей, правил площадок или upstream-изменений — реагируем по событию. Нет обязательной исследовательской активности ради её непрерывности.

**Разработка — отдельный контур.** **Стандартный цикл после временного периода:** цель → анализ GitHub-кода → явное разрешение пользователя → Codex → локальная проверка → независимое ревью ChatGPT → решение об интеграции. **До 04.11 включительно** действует цикл ChatGPT → GitHub task-ветка/draft PR → независимое ревью Codex → ChatGPT ACCEPT/REVISE/REJECT → разрешение пользователя на merge, определённый выше. Исследование само по себе не разрешает реализацию, API и merge.

**Статусы:** исследование `аналитически завершено` не означает `исправлено в коде`, `локальный PASS` не равен `успеху реальной модели`, а успешный G1 не гарантирует пригодность длинного романа. Один и тот же факт не должен иметь несколько конкурирующих «текущих статусов»: исследования — [RESEARCH_CURRENT_STATE.md](./RESEARCH_CURRENT_STATE.md), разработка — [CURRENT_STATE.md](./CURRENT_STATE.md), исторические решения — [DECISIONS.md](./DECISIONS.md).

**Историческое правило паузы отменено на 31.10–04.11.2026:** при уже согласованной кодовой задаче ChatGPT может довести подготовку до task-ветки и draft PR без Codex; Codex ревьюит позже. Исследовательский чат не начинает **несогласованную** реализацию только по слову «дальше».

## Кто что делает

- **Пользователь:** формулирует цель, определяет приоритеты и бюджет; разрешает кодовую реализацию, интеграцию, публикацию, рисковые действия; запускает локальные проверки самостоятельно либо разрешает конкретные команды локальному Codex.
- **ChatGPT:** читает GitHub и код, анализирует, выбирает решение в границах цели, ведёт ROADMAP и `fork-docs/`. **До 04.11 включительно** также реализует согласованный код в task-ветке GitHub и открывает draft PR; затем оценивает независимые замечания Codex и выдаёт **ACCEPT / REVISE / REJECT**. Приёмка **не** разрешает merge.
- **Codex (стандартный режим после 04.11):** основной исполнитель исходников, тестов и конфигураций. **Во временном режиме** его роль — независимая проверка уже подготовленного ChatGPT PR и узкие исправления по результатам; не повторять весь объём разработки. Не расширяет согласованную задачу.

## Основной режим: локальный Codex + облачный ChatGPT

- **Codex Desktop на Windows** редактирует и проверяет локальный репозиторий `C:\Projects\inkos` по отдельной согласованной задаче. Codex Cloud и ChatGPT Work не являются обязательной частью цикла.
- **ChatGPT в обычном чате** читает GitHub (`custom/main`, рабочие ветки, коммиты, PR и `fork-docs/`) и материалы, явно переданные пользователем. Локальный `git status`, stash, логи и незакоммиченные файлы ChatGPT автоматически не видит.
- Для значимых изменений использовать отдельную ветку и PR в `custom/main`. **Временно (до 04.11):** создание task-ветки, commit/push и draft PR входит в одно предварительное разрешение пользователя на конкретную кодовую задачу; повторно спрашивать на каждом шаге не нужно. **Merge всегда требует отдельного разрешения**; ACCEPT не равен разрешению на merge.
- Генерируемые проекты и рукописи хранить отдельно от публичного репозитория. Не отправлять пользовательские данные и секреты в GitHub ради удобства ревью.
- **Локальные артефакты ревью** (patch, отчёты) сохранять вне репозитория и вне временных каталогов в `C:\\Projects\\inkos-review-artifacts\\<идентификатор-задачи>\\`. Для ревью незакоммиченных изменений передавать полный patch, включая untracked-файлы; ссылки `C:\\...\\` недоступны обычному ChatGPT — прикладывать файл. После push предпочтительнее PR в GitHub. Запись вне sandbox — только по точечному разрешению.

## Практический цикл (стандартный после временного режима; активный цикл описан выше)

1. Пользователь описывает проблему или желаемое поведение.
2. ChatGPT исследует код **нужной ветки** и проверенный коммит, рекомендует минимальное решение, отмечает риски и критерии приёмки.
3. После согласия пользователя ChatGPT передаёт Codex задачу: **цель, границы, поведение, критерии приёмки**. Одного разрешения хватает на всю задачу.
4. Codex меняет только согласованное, проверяет дифф, перечисляет файлы, риски и **фактически выполненные** проверки.
5. ChatGPT предлагает минимально достаточные локальные команды **для Windows/pwsh**; пользователь выполняет их сам или поручает локальному Codex с явным разрешением. Отчёт содержит реальные PASS/FAIL и нужные строки лога.
6. ChatGPT делает независимое ревью. При REVISE возвращает узкое замечание Codex без нового масштабного рефакторинга; при ACCEPT рекомендует приёмку, но ждёт разрешения пользователя на интеграцию.
7. ChatGPT актуализирует `CURRENT_STATE.md`, `DECISIONS.md`, `ROADMAP.md` после значимых принятых изменений.

## Задачи, PR и планирование

- Мелкие исправления можно передавать Codex в чате без GitHub Issue.
- Для продолжительных/значимых задач Issue полезен как постоянная точка отсчёта. PR нужен для содержательного ревью, а не автоматически для каждого исправления.
- Codex Plan Mode — для межмодульной неопределённости, существенных рисков и сложных зависимостей; не повторять уже проведённый ChatGPT анализ.
- **Выбор моделей и делегирование:** [CODEX_PLAYBOOK.md](./CODEX_PLAYBOOK.md). Прежняя рабочая база — **Sol Medium**; **Terra Medium** пробовать на узких согласованных исправлениях, **Luna** — на исследовательском поиске, Sol сохранять для сложных/рискованных изменений. По умолчанию **один Codex**, субагенты только при независимых подзадачах, первоначально максимум два. Plan/Goal/Skills/команды и кастомные роли не дают дополнительных разрешений и не меняют границы задачи. Доступность модели и функций зависит от локального клиента; проектные или глобальные конфигурации без разрешения не менять.
- ROADMAP — ориентир, а не разрешение автоматически начинать новые задачи. Нет обязательных спринтов и сроков.

## Ограничения на тестирование

Без отдельного разрешения Codex **не запускает** `pnpm install`, build, test, lint, typecheck, E2E, Studio и повторяющиеся диагностические циклы. Разрешено читать и писать тесты в рамках задачи, анализировать код/дифф, рекомендовать команды.

Проверки выбираются по риску: обычно точечные; после группы изменений — по затронутым пакетам; полные — перед крупной интеграцией/релизом. Не объявлять тест PASS, если нет подтверждения. По FAIL — выяснить причину и дать точечное исправление.

## Работа с Git и данными

- Репозиторий: **NeuralDao/inkos**. Основная рабочая ветка — **custom/main**. `master` и `upstream-main` не загрязнять правками.
- Перед выводом проверить текущий commit/файлы GitHub; не считать локальную копию автоматически синхронизированной.
- Учитывать новые upstream-изменения, не применять их без анализа совместимости и разрешения.
- По умолчанию — только чтение. Не выполнять опасные команды, публикацию или платные LLM-эксперименты без явного согласия.
- **Не загружать** ключи, приватные рукописи и пользовательские рабочие данные в публичный репозиторий.

## Перенос контекста между чатами

Новый чат читает [INDEX.md](./INDEX.md) и **только соответствующий актуальный статус**: исследование — [RESEARCH_CURRENT_STATE.md](./RESEARCH_CURRENT_STATE.md), разработка — [CURRENT_STATE.md](./CURRENT_STATE.md). Далее — **один нужный тематический документ** или конкретный код/PR. Полный [RESEARCH.md](./RESEARCH.md), [ROADMAP.md](./ROADMAP.md), [DECISIONS.md](./DECISIONS.md) и остальные архивы **не загружать целиком по умолчанию**. Старые формулировки «следующий этап» внутри журналов относятся к дате записи; актуальный следующий шаг — в соответствующем CURRENT_STATE. Документация фиксирует только решения, факты, ограничения и следующий шаг; никакой стенограммы обсуждений.

**Постоянная норма после 04.11:** ChatGPT коммитит только `fork-docs/`; кодовая работа через Codex. **Временное исключение 31.10–04.11** прямо разрешает ChatGPT коммитить согласованные код/тесты в отдельную task-ветку и открывать draft PR, как описано в первом разделе. После 05.11 вернуться к постоянному режиму, если пользователь не продлит исключение.
