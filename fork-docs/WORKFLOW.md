# Рабочий процесс InkOS

## Роли

ChatGPT и Codex — равноправные участники разработки. Каждый может исследовать задачу, принимать согласованные в рамках цели технические решения, менять код и документацию, проверять и независимо рецензировать результат. Исполнитель и ревьюер выбираются по удобству текущей задачи; обязательного разделения по продукту или клиенту нет.

Пользователь определяет цель, приоритет, бюджет и границы рискованных действий. Согласованная реализация включает необходимые изменения кода и документации. Не начинать соседние задачи, крупные миграции, публикацию или интеграцию за пределами согласованного объёма.

## Репозиторий — источник общего состояния

- Рабочий репозиторий: `NeuralDao/inkos`, основная ветка разработки — `custom/main`; `master` и `upstream-main` остаются чистыми базовыми ветками.
- Перед работой проверить ветку, HEAD, рабочее дерево и актуальность относительно удалённого репозитория. Не считать разные локальные или облачные копии автоматически синхронизированными.
- Для параллельной или передаваемой между чатами работы использовать одну task-ветку. Синхронизировать код и статус через коммиты, push и PR; фиксировать актуальный следующий шаг и незавершённую работу в `fork-docs/CURRENT_STATE.md`. Не переносить состояние только пересказом в чате.
- Не перезаписывать чужие незакоммиченные изменения. Передавать или объединять работу через Git; при конфликте сначала изучить обе версии и сохранить их содержимое.
- Коммиты в task-ветку допустимы в рамках согласованной задачи. Не выполнять push, merge в защищённые ветки, rebase с переписыванием общей истории, force-push или публикацию без явного разрешения пользователя.
- PR использовать для содержательного обзора или интеграции, а не как обязательный шаг каждой небольшой задачи. Решение о merge остаётся за пользователем.

## Ход работы

1. Проверить `AGENTS.md`, этот документ и актуальный статус разработки или исследования.
2. Сверить исходную ветку/коммит и относящиеся к задаче файлы; кратко обозначить цель и границы.
3. Выполнить согласованную работу в удобной среде. Менять минимальный связный набор файлов; обновлять относящуюся документацию вместе с реализацией.
4. Проверить diff, статус Git и выполненные проверки. Для каждого теста, сборки или проверки явно указывать `PASS`, `FAIL` либо `NOT RUN`; не выдавать локальный результат за проверку пользовательской Windows-среды.
5. Передать результат другому участнику для независимого ревью, если это полезно по риску и масштабу. Ревьюер сообщает конкретные замечания; исполнитель исправляет их в той же task-ветке.
6. Синхронизировать итог и оставшиеся шаги в репозитории. Не выполнять merge или публикацию до решения пользователя.

## Разрешения и ограничения

- Согласованная задача разрешает необходимые в её границах изменения и точечные исправления. Новые продуктовые цели требуют согласования.
- Без отдельного конкретного разрешения не устанавливать/обновлять зависимости и не запускать тесты, сборки, lint, typecheck, E2E, Studio, CI, платные LLM/API-вызовы, генерационные эксперименты или внешнюю публикацию. Учитывать, что push/PR может автоматически запустить CI.
- Не включать в Git ключи, `.env`, секреты, приватные рукописи, пользовательские логи или чувствительные конфигурации. Рабочие книги держать отдельно от публичного репозитория.
- Основная целевая среда — Windows/PowerShell. Облачные проверки не подтверждают работу в локальной Windows-среде.
- Технический PASS не доказывает качество русской прозы; литературную пригодность оценивать отдельно на сохранённых артефактах.

## Продуктовые ограничения

1. Цель форка — качественная оригинальная литература на русском языке.
2. Русский текст может естественно включать имена, бренды, технические термины и цитаты в исходном написании. Не вводить проверки «только кириллица», насильственный перевод или транслитерацию.
3. Не разрабатывать переводческий конвейер, полную локализацию Studio, новые форматы или архитектуру «на вырост» без отдельного решения.
4. Сохранять штатные English/Chinese-пути InkOS, если их изменение не требуется согласованной задаче. Язык пользовательского текста задавать отдельным и непротиворечивым контрактом; не переводить скрытые рассуждения, внутренние Skills, JSON-ключи, технические ID и enum.
5. Не добавлять миграции и обратную совместимость без подтверждённого пользовательского сценария.

## Контекст между чатами

Новый участник читает `AGENTS.md`, этот файл, `fork-docs/INDEX.md` и актуальный статус по текущей задаче: `CURRENT_STATE.md` для разработки или `RESEARCH_CURRENT_STATE.md` для исследования. Затем читает только необходимые тематические документы и код. После значимых изменений обновляет статус и решения в репозитории, чтобы другой чат мог продолжить с проверенного коммита.
