# Принятые решения

Здесь только устойчивые договорённости и их причины. Если меняется решение, фиксировать новое с датой и пояснением, а не переписывать прошлое как будто его не было.

## 29 октября 2026 — назначение форка

**Решение:** развивать NeuralDao/inkos для оригинальной качественной русскоязычной серийной литературы с учётом интереса читателя, стоимости и будущих публикаций на Author.Today/Boosty. Переводческий конвейер не развивать без отдельного запроса.

**Причина:** сосредоточить ограниченное время и бюджет на главной цели проекта.

## 29 октября 2026 — управляемый вайб-кодинг

**Решение:** личный любительский проект без спринтов и корпоративных согласований. Пользователь определяет цели и санкционирует реализацию; ChatGPT выбирает техническое решение, планирует и ревьюит; Codex единственный изменяет код. Одного разрешения достаточно на согласованную задачу. Существенные расширения требуют согласования.

**Причина:** сохранять скорость, понятность и управляемость без избыточной архитектуры.

## 29 октября 2026 — границы GitHub

**Решение:** работать над кодом в `custom/main`; `master` и `upstream-main` сохранять чистыми как базы upstream. ChatGPT не изменяет исходники, конфигурации, тесты и CI. Исключение — самостоятельное ведение файлов в `fork-docs/` и согласованных Issues. Техническое ACCEPT не равно разрешению на merge.

**Причина:** воспроизводимые ревью, безопасное обновление upstream и чёткое разделение ролей.

## 29 октября 2026 — Windows прежде всего

**Решение:** основная среда разработки и запуска — Windows + PowerShell (`pwsh`). WSL2/Linux использовать лишь при подтверждённой необходимости, если разумного нативного или кроссплатформенного решения нет.

**Причина:** не усложнять локальную эксплуатацию ради Unix-зависимостей.

## 29 октября 2026 — экономия лимитов Codex

**Решение:** Codex по умолчанию не запускает установку зависимостей, сборку, тесты, lint, typecheck, E2E, Studio и повторяющиеся диагностические циклы. Проверки обычно запускает пользователь локально и сообщает PASS/FAIL. Исключения — по явному разрешению на конкретную проверку.

**Причина:** беречь лимиты Codex на реализацию и содержательное ревью.

## 29 октября 2026 — задания и документация

**Решение:** мелкие задачи — напрямую в Codex; значимые и долгие — через Issues по необходимости; Plan Mode — лишь при реальной неопределённости/риске, не дублировать готовый анализ ChatGPT. GitHub `fork-docs/` — первичный источник изменяемой документации, а Project Sources — для редких долговременных материалов.

**Причина:** при переходах между чатами сохранять решения и текущую точку работы без копирования переписки. Детали — в [WORKFLOW.md](./WORKFLOW.md).

## 29 октября 2026 — локальный Codex, облачный ChatGPT и GitHub как канал ревью

**Решение:** основной исполнитель — локальный Codex на Windows; ChatGPT остаётся обычным облачным чатом с подключённым GitHub, без обязательного Work или Codex Cloud. Существенные кодовые изменения передаются на независимое ревью через GitHub PR. Локальные тесты допускаются только с точным разрешением пользователя. PR и merge требуют согласования; приватные рукописи и секреты не публикуются.

**Причина:** проверка в целевой Windows-среде, экономия лимитов и воспроизводимый независимый обзор диффа. Подробности — в [WORKFLOW.md](./WORKFLOW.md).

## 29 октября 2026 — русский текст без перевода внутреннего конвейера

**Решение:** сохранить встроенные англоязычные инструкции, Skills, служебные структуры и форматы InkOS 2.0. Целевой язык **читательского литературного вывода** — русский, при сохранении английского языка служебных планов, карточек и состояния. Не навязывать глобально русский всем текстовым полям и инструментам. Предпочесть точечные инструкции Writer/Reviser и при необходимости минимальный отдельный контракт языка результата. Для скрытого рассуждения модели язык не задавать как проверяемое требование.

**Причина:** на версии 1.8 пользователь наблюдал стабильную русскую прозу при англоязычных внутренних материалах; полная русификация проверенных алгоритмов увеличивает риск регрессий и расход разработки. В 2.0 структура вызовов агентов изменилась, поэтому старые патчи `dist` переносить нельзя.

**Связанный технический факт:** 1.8 требовала обхода `inferLanguage()` для кириллицы, а счётчики `en_words` не покрывают русскую прозу. В 2.0 нужно рассматривать выбор рабочего языка и Unicode-метрики **отдельными задачами**. Подтверждённые точки — [ROADMAP.md](./ROADMAP.md) и [ARCHITECTURE.md](./ARCHITECTURE.md).

## 29 октября 2026 — технические ID книг с кириллицей

**Решение:** для русских названий единообразно формировать безопасные ID в Core и Studio, не менять само название. Непригодное для ID название отклонять с явной ошибкой, а не создавать случайный `book-<timestamp>` в согласованных точках CLI/Core. При явно заданном безопасном ID в Core сохранять существующее поведение. Решение реализовано в [PR #2](https://github.com/NeuralDao/inkos/pull/2), merge `3461353d`; локальные точечные проверки — 43 PASS по отчёту Codex.

**Причина:** устранить различия между точками создания книг и получить предсказуемые русские ID без изменения языкового конвейера.

## 29 октября 2026 — постоянное хранение материалов ревью

**Решение:** патчи и отчёты до публикации PR сохранять вне репозитория в `C:\\Projects\\inkos-review-artifacts\\<идентификатор-задачи>\\`, а не в `Temp`. Для обычного ChatGPT прикладывать patch-файл; после push работать по GitHub PR. Не предоставлять Codex постоянные расширенные разрешения только ради этого каталога.

**Причина:** временный patch P1.1a исчез до независимого ревью; постоянное расположение делает процесс воспроизводимым и не загрязняет Git.

## 29 октября 2026 — контракт языка longform P1.1b

**Решение:** разделить рабочий язык InkOS (`book.language: en | zh`) и язык читательской прозы (необязательный `book.narrativeLanguage: en | zh | ru`). Если второе поле не задано, действует `book.language`; для `ru` без явного операционного языка выбирать `en`, явный конфликт `zh + ru` отклонять. Передавать контракт через CLI, Studio, Core и Work metadata, не менять глобально язык служебных инструкций, Skills и схем. Реализовано в [PR #3](https://github.com/NeuralDao/inkos/pull/3), merge `24bdd47c6891c61057ca3c250edd490708f5f8bc`.

**Причина:** готовить русский литературный вывод без переустройства англоязычного конвейера и без регрессии существующих EN/ZH-сценариев. Само качество русской генерации проверяется на последующих этапах.

## 29 октября 2026 — отказ от необязательной legacy-совместимости

**Решение:** ориентироваться на актуальный формат данных InkOS 2.0. **У пользователя нет существующих книг или проектов InkOS вообще, в том числе старых версий; переносить нечего.** Миграции устаревших форматов, поддержка исторических интерфейсов, backward compatibility и адаптеры ради старых пользовательских книг **не обязательны**; добавлять их только при конкретной практической потребности. Нельзя усложнять новую схему исключительно ради вызовов старых механизмов. В P1.1b legacy-миграция использует строгую `BookConfigSchema.parse()` вместо `.strip().parse()`: неизвестные поля старых книг могут отклоняться, это принятое ограничение. Существующие актуальные EN/ZH-функции не удалять автоматически.

**Причина:** это личный форк без существующих проектов или накопленных пользовательских данных InkOS; поддержание гипотетических прошлых форматов расходует ресурсы без пользы. Приоритет — простота реализации, надёжность и минимальная стоимость сопровождения. Это не требование удалять или ломать актуальные служебные механизмы InkOS 2.0.

## 30 октября 2026 — русский как единственный художественный язык форка

**Решение пользователя:** NeuralDao/inkos предназначен **только для оригинальной литературы на русском языке**. Генерация англоязычных или китайскоязычных романов не является продуктовой целью, даже если InkOS 2.0 сохраняет внутренние `language: en | zh` и ранее введённый `narrativeLanguage: en | zh | ru`. Эти технические контракты не удалять автоматически в рамках P1.2; упрощение выбора языков в UI/API рассматривать отдельно, если это действительно снижает сложность.

**Русская проза допускает иностранные написания** имён, названий брендов и компаний (например, Nike и Microsoft), космических аппаратов, технических систем (например, Apollo-1), аббревиатур, кодов, моделей, команд и терминов, когда это естественно для жанра, мира и канона. Не требовать исключительно кириллицу и не навязывать машинный перевод/транслитерацию. Явно заданные автором точные названия и закреплённые каноном написания сохранять; английские внутренние планы сами по себе не делают все латинские написания обязательными.

**Техническая политика:** для longform основной сценарий — `book.language=en`, `book.narrativeLanguage=ru`: английские встроенные инструкции, Skills и служебное состояние, русский читательский текст. Язык скрытых рассуждений модели не контролируется и не является проверяемым контрактом. P1.2a/b прежде всего проверять на RU-генерации и сохранении смешанной письменности; не тратить ресурс на улучшение EN/ZH-художественного вывода, но не ломать существующие общие механизмы без необходимости. Unicode-метрики P1.3a должны считать смешанный русский/латинский текст корректно, без эвристики «только кириллица».

**Причина:** целевой продукт — качественная естественная русская литература, включая научно-фантастические, исторические, корпоративные и технические сюжеты с правдоподобными собственными именами и обозначениями. Расход на универсальную многоязычную литературную генерацию не оправдан.

## 30 октября 2026 — эталонный литературный прогон longform, а не тестовый роман

**Решение:** для контрольных платных испытаний использовать **один оригинальный законченный рассказ в штатном профиле `longform-novel`**: план **5 глав по 1350 русских слов**, допустимый ориентир 1200–1500 без жёсткого требования переписывать главы из-за небольшого отклонения. **G1:** независимый запуск первых 3 глав; **G2:** проверка отчётов на сохранённых главах без новой книги; **G3:** новый прогон первых 4 глав; **G4:** новый полный прогон 5 глав с развязкой. Примерный объём оплачиваемого читательского текста на G1/G3/G4 — 14 400–18 000 слов суммарно, **без** учёта затрат на Architect, Planner, Auditor, Reviser, состояние, повторы и контекст. Запуск всех этих этапов не разрешён этой записью: бюджет и модели утверждаются отдельно.

**Два разных эталона:** (1) одно неизменное исходное **авторское литературное задание**, из которого штатный Architect сам создаёт основу; (2) **версионируемая** конфигурация моделей, провайдеров и параметров агентов. На G1 стек первоначально лишь кандидат и становится историческим baseline v1 после успешного платного прогона. Для сравнения изменений InkOS по возможности держать стек постоянным; для сравнения моделей — версию InkOS и исходные условия. Исходную спецификацию не подменять сохранённой прозой модели; сохранять созданную Architect основу отдельно, чтобы отличать изменения подготовки книги от изменений Writer/Reviser. Повторение с LLM вероятностно; одиночные сравнения не доказывают превосходство.

**Причина:** законченный компактный рассказ проверяет завязку, последствия, перелом, кульминацию, развязку, аудит и канон существенно дешевле полноценного романа; тот же вход позволяет сравнивать версии форка по перекрывающимся главам. Подробности и исторический путь Studio 1.8 → 2.0 — [BENCHMARK_LONGFORM.md](./BENCHMARK_LONGFORM.md).

## 30 октября 2026 — литературное качество важнее инфраструктуры исследований

**Решение:** сохранять нативные механизмы и инструкции InkOS насколько возможно. Три рабочих рычага улучшений: (1) фактически проверенные модели и их настройки, (2) точечные изменения инструкций Writer/Reviser после выявления литературных дефектов, (3) полнота и согласованность межагентного контекста. Не усложнять архитектуру и промпты без сопоставимых примеров. Пользоваться существующими Vitest-моками и fake-API; **не создавать универсальный proxy, отдельный benchmark-сервис или обязательный слой локальной микромодели** без конкретного доказанного пробела. Микромодель допускается как необязательный эксперимент на CPU после измерения её поведения; платные G1–G4 обязательны и отдельно ограничены бюджетом.

**Причина:** проект остаётся управляемым вайб-кодингом ради качественной оригинальной русской прозы, не второй работой по обслуживанию тестовой платформы. Исследования и новые абстракции должны устранять конкретный риск, а не становиться самоцелью. Подробности: [RESEARCH.md](./RESEARCH.md), [RESEARCH_LLM_OFFLINE.md](./RESEARCH_LLM_OFFLINE.md), [ROADMAP.md](./ROADMAP.md).

## 30 октября 2026 — рабочий эталон R3 v1.0 и компактный R4

**Решение:** зафиксировать **один** точный оригинальный авторский ввод «Последняя ведомость» v1.0 в [BENCHMARK_LONGFORM.md](./BENCHMARK_LONGFORM.md) для будущих G1/G3/G4. Сохранять 5 глав по 1350 русских слов, ограниченный ресурс (12 безопасных мест при 13 ожидающих), один рейс до 19:00, неравное знание героев, ошибочную ведомость и официальное название `RiverLine` в латинице. Не предписывать одно морально правильное решение: оценивать **объяснимость** действий и реальность последствий. Вход после использования нельзя подменять без новой версии; исторический v0 остаётся в исследовании R3.

**R4:** хватит одной приватной карточки прогона и одной A/B-карточки на сравнение перекрывающихся глав с конкретными свидетельствами по R2, отделением расходов по агентам и допущением «недостаточно данных». Не внедрять дополнительный eval-сервис или обязательного LLM-судью. R2/R4 пока не калиброваны на настоящем тексте; подготовка тестового задания **не означает разрешения на платный G1**.

**Причина:** получить сравнимые и экономичные данные о художественном качестве InkOS, не превращая хобби в тестирование произвольных запретов и построение инфраструктуры ради неё самой.

## 30 октября 2026 — Selectel AI Router и право на обоснованную инвазивную адаптацию

**Выбор пользователя:** единственный **плановый** API-роутер G1 — **Selectel AI Router** (`selectel.ru`), а не OpenRouter. Для планирования найден в личной библиотеке ChatGPT файл `airouter-daily-price.pdf` с рублёвыми тарифами за 1 млн токенов (включая НДС) на **12.10.2026, 11:02 МСК**; перед реальной оплатой проверить актуальные цены/алиасы/поддержку инструментов в панели Selectel. Прайс не является API-документацией и не подтверждает успешную работу конкретных моделей. PDF и пользовательские данные **не копировать** в публичный GitHub. Ранее изученный OpenRouter — исторический вариант исследования, не настройка G1.

**Политика вмешательства:** прежнее предпочтение «сохранять upstream и делать минимальные изменения» **не запрещает инвазивную адаптацию**, если исходные облачные допущения, системные/агентные инструкции, схемы, provider-совместимость либо маршрутизация мешают корректной работе с Selectel или качественной русской литературе. Предположение о жёсткой провайдерской заточке InkOS — **гипотеза**, проверять по коду и конкретным симптомам. Устанавливать минимальную **достаточную** глубину изменений, а не отказываться от нужных правок ради небольшого diff. Границы согласовываются с пользователем; код/тесты меняет только Codex, ChatGPT независимо ревьюит. Без доказанного дефекта не разворачивать «архитектуру на будущее».

**Почему:** целевой результат — хорошая экономичная оригинальная русская проза на реальном Selectel-стеке, а не идеальная обратная совместимость с исходными поставщиками. Порядок проверок и выбранные кандидатные тарифы: [RESEARCH_R6_MODELS.md](./RESEARCH_R6_MODELS.md).

## 30 октября 2026 — стоимость по входу/выходу и выбор reasoning на уровне ролей

**Решение пользователя:** для мультимодельного G1 учитывать не только качество и стоимость модели в целом, но и соотношение **прочитанных входных / сгенерированных выходных** токенов конкретного агента, кэш, повторы и возможные reasoning-токены. Входоёмким проверяющим/структурным агентам искать дешёвый input, длинногенерирующим — не игнорировать цену output. По возможности не оплачивать reasoning там, где структурная задача решается без потери качества; пока точный per-agent native контроль Selectel не доказан, использовать Instruct/low-CoT **как проверяемых кандидатов, а не как гарантию нулевых thought-токенов**.

**Исследовательское разделение:** [R6(c)](./RESEARCH_R6_TOKEN_ECONOMY.md) — статическая модель стоимости **до G1**, [R6(b)](./RESEARCH_R6_MODELS.md) — фактическая экономия **после G1** по биллингу и качеству принятой главы. В InkOS есть глобальный thinkingBudget, но per-agent override нет; Writer и Settler используют общую модель при разных нагрузках. Код при необходимости адаптировать по отдельному согласованию через Codex. Не включать дополнительные платные проверки и не проектировать новый router только ради сравнения цен.

## 30 октября 2026 — закрытие подготовительной R6 и единый кандидат стека G1 v0

**Решение:** прекратить дальнейший подбор моделей «на бумаге» до появления реальной русской прозы; зафиксировать **один [кандидат G1 v0](./G1_MODEL_STACK.md)** под Selectel: Architect/Auditor/StateValidator — DeepSeek V3.2; Planner и условные LLM-вызовы Composer — Qwen3 235B Instruct; Writer — Qwen3.5 397B; Reviser — MiniMax M2.5. Целевой Settler — Qwen3 Instruct, но текущий Settler наследует Writer, и его разделение **не безусловный блокер** G1. Точные aliases, рабочее reasoning/toolChoice и цены требуют технической и платной проверки по отдельному разрешению.

**Основание:** модель нагрузки по коду и историческая Selectel-выписка InkOS 1.8 за четыре главы. Она подтверждает высокий суммарный объём входного контекста, но не связывает расходы с конкретными агентами; старый PDF не воспроизводит фактические начисления по одной исторической модели. Частная выписка/идентификаторы/точные пользовательские расходы **не публикуются**.

**Статус:** R6(a) и R6(c) закрыты **аналитически**; R6(b) — только **после G1**, когда будут сведения о фактической стоимости и качестве каждого этапа. Это **не разрешение** на код, CI, Selectel API и расходы. Следующий практический путь — P1.2b → P1.3a/b → P1.M → локальная проверка → согласованный G1.

## 30 октября 2026 — отдельный статус исследований и режимная граница

**Решение:** исследования InkOS продолжаются **по конкретным вопросам и после контрольных литературных прогонов**, а не непрерывно ради количества R-этапов. Создать [RESEARCH_CURRENT_STATE.md](./RESEARCH_CURRENT_STATE.md) как короткую текущую точку входа исследовательского чата. [CURRENT_STATE.md](./CURRENT_STATE.md) остаётся инженерным статусом, [RESEARCH.md](./RESEARCH.md) — планом/журналом, [ROADMAP.md](./ROADMAP.md) — инженерным планом. **Разработка на паузе до возвращения пользователя к компьютеру с Codex.** Фразы «продолжай/двигаемся дальше» в исследовательском чате не разрешают реализацию. R7b допустимо исследовать сейчас, но она не блокирует G1; R6(b) после реальных G1-данных. Исследовательские чаты не запускают Codex, CI, Studio и платные API. Причина: исключить смешение двух разных очередей и сохранить лёгкую навигацию без дублирования отчётов.

## 30 октября 2026 — аудит базы знаний: исследования как постоянный контур, быстрая навигация

**Решение:** поддерживать **две равноправные линии**: (1) исследования качества, моделей, стоимости, площадок и новых рисков — регулярные по событиям/G1/G3/G4, **без обязательного непрерывного исследования**; (2) реализация Codex с отдельным разрешением. Только [RESEARCH_CURRENT_STATE.md](./RESEARCH_CURRENT_STATE.md) указывает текущую исследовательскую тему и триггеры; только [CURRENT_STATE.md](./CURRENT_STATE.md) — текущую инженерную задачу. [INDEX.md](./INDEX.md) — короткий роутер в эти статусы и тематические источники, [RESEARCH.md](./RESEARCH.md) — подробный архив/реестр проходов, [ROADMAP.md](./ROADMAP.md) — инженерные зависимости, [WORKFLOW.md](./WORKFLOW.md) — роли и правила. Исторические «следующие шаги» не интерпретировать как новые указания. Не читать полные журналы/ROADMAP и все документы в начале каждого чата; достаточно INDEX + соответствующего CURRENT_STATE + материала по запросу.

**Основание:** аудит всех 19 файлов `fork-docs/` на `custom/main@59446a5f`: внутренних несуществующих ссылок не найдено, но входная навигация была преимущественно инженерной; журнал R0–R6 содержал устаревшие «следующие шаги», старый архитектурный аудит описывал P0/P1.1b как ещё не выполненные. Документы-источники сохраняют исторический смысл с пометкой о дате; актуальные указатели и статусы уточнены. **Цель документации — дешёвая и достоверная координация следующих чатов, не отчётность для внешнего руководителя.**
